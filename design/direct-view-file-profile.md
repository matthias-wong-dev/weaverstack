# Saved Spark View file profile (experimental)

Fabric [stores schema-enabled Spark Views as OneLake files](https://learn.microsoft.com/en-us/fabric/data-engineering/lakehouse-spark-views). That documentation identifies a View property but does not specify a contract for external file writers.

## Observed runtime profile

A Spark-created, source-backed View in the trial runtime had a 15-field JSON document, 7,258 decoded bytes and 1,888 deflate-encoded bytes. Its headers were `Content-Type: application/json`, `Content-Encoding: deflate`, and `x-ms-properties: xCatalogMetadataVersion=MjAyNDA1,xCatalogTableType=VklFVw==`. The JSON carries `tableType: VIEW`, the original query, output column names/types/nullability, a `createVersion` build string, an opaque catalogue namespace and 70 captured Spark SQL configuration entries. A retained View had an additional case-sensitivity entry. Neither the opaque namespace nor the build string is generated by Weaver.

The original probe passed fresh Spark discovery, `SHOW CREATE TABLE` on the View, row reads and dependent queries for a directly written View. Spark subsequently replaced another directly written View. A plain, uncompressed JSON file with the View marker was listed but could not be queried. These observations establish compatibility in one trial, not stability across service patches or a supported writer API.

## Candidate route

On desktop Build, the Session uses Spark to create the first View in each target Lakehouse schema. It reads that exact file and accepts only the observed structural fields, namespace properties, MIME, encoding and marker. Unknown profiles retain Spark creation. The Session analyses remaining View queries' Spark schemas in one labelled submission for independent siblings. It compiles each query and its actual output shape against the live template. Unsupported shapes retain Spark creation.

For a qualified View, the Session writes compressed JSON to a unique private `Files` stage. It checks the stored bytes and headers, then renames the file to an absent `Tables/<schema>/<name>` destination with no-overwrite and source-ETag conditions. Final read-back confirms the bytes and headers. A lost rename response is reconciled against the final file; an uncertain destination fails without a Spark retry. Independent Views in one Installer dependency batch and Lakehouse schema can publish concurrently through a bounded desktop Session worker pool. The template and shape reads stay on the foreground Session. The pool drains before Spark fallback, another schema group or a dependent batch; results remain in action order. The renewing default OneLake token provider serialises refresh across these workers, while a caller-supplied token callable retains its caller-owned threading contract. The ordinary Session implementation uses Spark, including in a Fabric notebook. The Build manifest and public API are unchanged.

A live template limits format and namespace drift within a Session. It cannot establish Microsoft support for external writes or guarantee compatibility within Fabric runtime 2.0. Microsoft's guidance is needed on whether this representation is stable within a runtime, what marks a supported writer, and whether a public saved-View creation API is planned.
