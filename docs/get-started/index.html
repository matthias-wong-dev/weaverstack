Get started

From nothing to a working pipeline

By the end of this page you will have a Weaver project in your own Fabric workspace, with a small Sales example built, loaded and tested. It takes one install and one command. Everything you need is here.

Before you begin

You need three things:

  • A Microsoft Fabric workspace you can already reach, on a capacity that is running.
  • Python 3.11 or later, if you are working from your own machine. A Fabric notebook already has it.
  • Permission to create items in that workspace, so Weaver can make the ones your project asks for.

You do not need a JDK, a local Spark install, or the Azure CLI. Fabric supplies Spark, and Weaver can sign you in through your browser.

Choose how you want to work

Weaver runs in two places and both are complete. Pick whichever suits you. The rest of this page is the same either way.

Option A

From a Fabric notebook

Stay inside Fabric. Open a notebook in your workspace, install Weaver into it, and set the project up from there. The workspace is the one the notebook is already running in, so you do not have to name it.

notebook cell
%pip install weaverstack
notebook cell
from pathlib import Path
import weaver

weaver.initialise(
    Path("builtin") / "repository",
    catalogue="Catalogue",
    environment="Weaver",
    lakehouse="Landing",
    warehouse="Curated",
    example=True,
)

Pass install_weaver=True as well if the Environment does not exist yet, or exists without Weaver in it. That is the same consent the desktop prompt asks for, and it takes about five minutes.

Option B

From the desktop CLI

Work from VS Code, a terminal, or wherever you keep your repositories. The one install gives you both the library and the weaver command.

terminal
pip install weaverstack
weaver initialise

Run it on its own and it asks you what you want, one question at a time. Nothing is created until you have answered them all.

Signing in is part of the install and nothing more. Weaver uses your Azure CLI sign-in if you have one, and otherwise opens Microsoft sign-in in your browser and remembers it, so the next command opens nothing.

Setting the project up

Here is what weaver initialise asks, and what each answer decides.

weaver initialise
Set up a Weaver project.

You'll use your Fabric workspace and choose the items you want for this project.
Any missing items will be created automatically.

Fabric workspace: My Fabric Workspace
Catalogue [Catalogue]:

Fabric Environment:
  1. Use an existing Environment
  2. Create a new Environment

Choose [1/2]: 2
Environment name [Weaver]:

Lakehouse [skip]: Landing
Warehouse [skip]: Curated
Would you like to create and run a small Sales example? [Y/n]:

What you are choosing

  • Workspace. An existing Fabric workspace. This one has to be there already.
  • Catalogue. A Warehouse where Weaver keeps its own tables, under the _ schema. It can be a Warehouse of its own or one you already use for your own schemas. Weaver owns _ in it and nothing else.
  • Environment. The Fabric Environment your project runs against, with Weaver installed in it. Use one your workspace already has, or make a new one.
  • Lakehouse and Warehouse. Where your objects get built. Choose one, or both. A project with neither has nowhere to build into.
  • The Sales example. A small working project so you can see the whole thing run.

Naming an item is how you ask for it. If it does not exist, Weaver creates it. If it does, Weaver uses it. That is also why a run that stopped halfway is safe to repeat: the second run picks up whatever the first one left.

Installing Weaver into a Fabric Environment takes about five minutes. It is the one real wait in the whole process, so Weaver asks before spending it:

weaver initialise
Environment 'Weaver' will be created and Weaver will be installed in it.

Installing Weaver in Fabric can take about 5 minutes.

Would you like to continue? [Y/n]:

Or say it all up front

The same run written out, which is the form to keep in a script:

terminal
weaver initialise \
  --workspace "My Fabric Workspace" \
  --catalogue Catalogue \
  --environment Weaver \
  --lakehouse Landing \
  --warehouse Curated \
  --example

Written out like that, nothing is asked, so the Environment has to be one that already has Weaver in it. Run weaver initialise on its own to be asked, or prepare the Environment first.

Want to see what would happen without changing anything? Add --dry-run.

What you get

A project of your own, and if you asked for the example, a small Sales pipeline in it. Here is the whole thing.

my-project/
workspace-config.yml
compose.yml

Lakehouse/Landing/
├── Files/
│   └── Sales__Customers.py
├── Tables/
│   └── Sales__Customer.py
└── assumptions/
    └── Sales__CustomerValid.py

Warehouse/Curated/
├── shortcuts.yml
├── Sales.Region.sql
├── Sales.CustomerByRegion.sql
└── assumptions/
    └── Sales.CustomerByRegionValid.sql

Two files describe the project itself. workspace-config.yml says which Fabric workspace and items to use:

workspace-config.yml
# One file describes one Fabric workspace.
#
# Weaver items are the keys under targets:, and each value is the Fabric
# item it is built into. Point the project at another workspace by
# copying this file and changing the names.
workspace: My Fabric Workspace
environment: Weaver

# Weaver keeps its own tables in the _ schema of this Warehouse, and
# owns nothing else in it.
catalogue: Warehouse/Catalogue

targets:
  Lakehouse/Landing: Landing
  Warehouse/Curated: Curated

Point the project at a different workspace by copying that file and changing the names. Your objects do not change. The Weaver item Lakehouse/Landing stays what it is, and only the Fabric item it is built into moves.

compose.yml names a sequence you can run as one command:

compose.yml
# A named sequence, run in one session:
#
#   weaver compose full
#
# Each entry takes the workspace the composition resolved, so none of
# them names it again. Naming no item builds, loads and tests every
# item workspace-config.yml declares.
compose:
  full:
    - build
    - load
    - test

The example code

Six small files. Have a look at what they say, because it is most of what there is to learn about writing Weaver objects. Nothing here declares an order.

Lakehouse/Landing/Files/Sales__Customers.py
"""
Folder ID: Sales.Customers

Description: Customer records as the sales system exports them.

Lineage: Stands in for the nightly export from the sales system.

File key: "*.csv"

Incremental: false

Notes: |
  A real deployment fetches the export here, over SFTP or from an API. This one
  writes the file itself, so the project loads with nothing set up beside it.
"""

from weaver import Folder

#: The export this example stands in for.
CUSTOMERS = """\
Customer id,Customer name,Region code
C001,Harbour Freight Pty Ltd,NSW
C002,Riverside Grocers,VIC
C003,Tablelands Coffee Roasters,QLD
C004,Coastal Marine Supplies,NSW
"""


class Sales__Customers(Folder):
    def read(self):
        # Weaver issues the staging directory and empties it before read() runs,
        # so a folder fills what it was given and returns it.
        with self.staging_folder() as staging:
            (staging.path / "customers.csv").write_text(CUSTOMERS, encoding="utf-8")
        return staging, []

A Folder brings files in. This one writes the export itself so the project loads with nothing set up beside it. A real one fetches over SFTP or from an API. Weaver issues the staging directory and empties it before read() runs.

Lakehouse/Landing/Tables/Sales__Customer.py
"""
Table ID: Sales.Customer

Description: One row per customer in the sales system.

Lineage: $Files/Sales.Customers

Primary key: Customer id

Comparison columns: Customer name, Region code

Schema:
  Customer id: string
  Customer name: string
  Region code: string

Notes: |
  Read from the export folder, so the table can be rebuilt from files that were
  kept.
"""

from Files.Sales__Customers import Sales__Customers

from weaver import Table


class Sales__Customer(Table):
    def read(self):
        # spark_path() is the abfss:// form Spark reads. path() is the mounted
        # pathlib.Path for ordinary Python.
        exported = Sales__Customers(self).spark_path()
        return (
            self.spark.read.option("header", True)
            .csv(exported)
            .selectExpr("`Customer id`", "`Customer name`", "`Region code`")
            .dropDuplicates(["Customer id"])
        )

A Delta table built with Spark. The dependency is the import at the top: from Files.Sales__Customers import Sales__Customers. That is all Weaver needs to know this table loads after that folder.

Warehouse/Curated/Sales.CustomerByRegion.sql
/*
Table ID: Sales.CustomerByRegion

Description: Customers with the name of the region they belong to.

Lineage: $Sales.Customer

Primary key: Customer id

Comparison columns: Customer name, Region name

Schema:
  Customer id: varchar(50)
  Customer name: varchar(200)
  Region name: varchar(100)

Notes: |
  Weaver reads the dependencies out of the query, so this table loads after both
  the customers and the regions it selects from.
*/

select c.[Customer id]
     , c.[Customer name]
     , r.[Region name]
  from [Sales].[Customer] c
  join [Sales].[Region] r on r.[Region code] = c.[Region code];

Ordinary T-SQL. No Jinja, no macros, no ref(). Weaver reads the dependencies out of the query itself, so this table loads after both the customers and the regions it selects from.

Warehouse/Curated/shortcuts.yml
# A Lakehouse table, made addressable inside the Warehouse.
#
# The Warehouse cannot read Delta files; it reads the Lakehouse's SQL endpoint.
# Declaring the shortcut lets a Warehouse object select from a Lakehouse object
# without either item knowing where the other is built.
logical:
  Warehouse/Curated/Sales.Customer: Lakehouse/Landing/Tables/Sales.Customer

A Warehouse cannot read Delta files directly. Declaring the shortcut makes the Lakehouse table addressable inside the Warehouse, so a Warehouse object can select from a Lakehouse object without either item knowing where the other is built.

Warehouse/Curated/assumptions/Sales.CustomerByRegionValid.sql
/*
Assumption ID: Sales.CustomerByRegionValid

Description: Every customer landed in a region the estate declares.

Notes: |
  A T-SQL validation compiles to a procedure anyone can run without Weaver:

      exec [_].[Assumption Sales.CustomerByRegionValid];
*/

select [Customer id]
     , [Customer name]
  from [Sales].[CustomerByRegion]
 where [Region name] is null;

An Assumption states something you are relying on, and returns the rows that contradict it. Holding looks like an empty result. This one compiles to a procedure anyone can run without Weaver.

Run it

Three commands, from the project directory. Each one reads workspace-config.yml sitting beside it, so there is nothing else to pass.

terminal
weaver build
weaver load
weaver test

  1. Build makes Fabric match your repository

    It creates the schemas, the folders, the Delta tables, the Warehouse tables and views, the shortcuts and the runnable load code, and it registers all of it in the Catalogue. Build changes structure. It does not move any data.

  2. Load runs the data work

    Weaver reads the graph it installed and runs each object in dependency order. The export folder fills, the Delta table reads it, the shortcut makes those customers visible in the Warehouse, and the join runs last.

  3. Test runs your checks

    The two Assumptions run against what was just loaded, and the result is recorded in the Catalogue rather than only printed.

Because the generated project ships a compose.yml, you can also run all three in one session:

terminal
weaver compose full

In a notebook

The same three operations, as functions. They read the project the same way:

notebook cell
import weaver

weaver.build()
weaver.load()
weaver.test()

Then ask how it is going

Once something is installed and loaded, Weaver can tell you whether the estate is currently healthy, which is a different question from whether the last command succeeded.

terminal
weaver health

Read what build, load, test and health actually do →

This is what Weaver sees

You wrote six files and none of them said what runs first. Weaver read the Python imports, the SQL relations and the shortcut declaration, and built one graph out of them. Files, Python tables, shortcuts, Warehouse SQL and validations are all in it.

This is the graph Weaver uses for everything afterwards. Loading walks it in order. A rebuild uses it to work out what a change affects. Health uses it to tell you when something is behind the things it reads.

Having trouble connecting?

If a command cannot reach Fabric, this is the one to run. It checks the connection and nothing else.

terminal
weaver doctor

On its own it proves your sign-in and the Fabric REST API. Run it from a project directory and it also checks the endpoints that project actually uses: TDS for each Warehouse, OneLake for each Lakehouse, and a Spark session where a Lakehouse is configured.

weaver doctor
  Fabric REST                       OK
  Workspace My Fabric Workspace     OK
  Warehouse/Catalogue TDS           OK
  Lakehouse/Landing OneLake         OK
  Spark session                     OK

Everything checked is reachable.

Where a check fails, the reason and what to do about it come with it. Checking a Lakehouse starts a Fabric Spark session, so give that one about a minute.

A different kind of problem: your repository, not your connection. weaver check reads your source and contacts Fabric not at all. Use it when a build complains about something you wrote.
