Get started

By the end of this page you will have a Weaver project in your own Fabric workspace, with a small Sales example built, loaded and tested.

Before you begin

You need:

  • A Microsoft Fabric workspace you can reach, on a running capacity.
  • Python 3.11 or later if you are working from your own machine. A Fabric notebook already provides it.
  • Azure authentication through the Azure CLI or Microsoft sign-in in a browser.

Setup can reuse existing Lakehouses, Warehouses and Environments. Creating a new Fabric item requires the relevant workspace permission.

Choose how you want to work

Start from a Fabric notebook or from the desktop CLI. You get the same project either way, and the rest of this page applies to both.

Option A

From a Fabric notebook

Open a notebook in your workspace, install Weaver into it and set the project up from there. Weaver uses whichever workspace the notebook is already running in, so you do not have to name one.

notebook cell
%pip install weaverstack
notebook cell
from pathlib import Path
import weaver

weaver.initialise(
    Path("builtin") / "repository",
    catalogue="Catalogue",
    environment="Weaver",
    lakehouse="Landing",
    warehouse="Curated",
    example=True,
)

Initialise writes source and creates or reuses items. Publication is deferred by default. Pass publish_environment=True to publish after setup. Build, load and test run separately.

Option B

From the desktop CLI

Work from VS Code, a terminal, or wherever you keep your repositories. One install gives you the library and the weaver command.

terminal
pip install weaverstack
weaver initialise my-project

Run weaver initialise my-project to create or reuse that folder. Weaver collects the project settings before creating any missing Fabric items.

The desktop CLI tries Azure CLI credentials first and opens Microsoft sign-in in a browser when needed. On a machine with secure credential storage, later commands reuse that sign-in until Microsoft requires you to authenticate again.

What you are choosing

  • Workspace. A Fabric workspace. This is the one thing that has to be there already.
  • Catalogue. The Warehouse where Weaver keeps its own tables, in the _ schema. Give it one of its own, or use a Warehouse you already have, since Weaver owns _ and nothing else in there.
  • Environment. The Fabric Environment your project runs against, with Weaver installed in it. Use one you already have, or make a new one.
  • Lakehouse and Warehouse. Where your objects are built. Choose a Lakehouse, a Warehouse, or both. Weaver requires at least one destination item.
  • The Sales example. A small working project you can build, load and test straight away.

Setup can select existing items or create new ones. Run weaver initialise my-project again after an interrupted attempt; Weaver reuses items already created. Add --dry-run to see what setup would create without changing anything.

README.md explains the local workflow. The Environment directory contains packages and compute settings, including those imported from an existing Environment. workspace-config.yml says which Fabric workspace and items to use:

workspace-config.yml
workspace: My Fabric Workspace
environment: Weaver
catalogue: Warehouse/Catalogue

targets:
  Lakehouse/Landing: Landing
  Warehouse/Curated: Curated

To point at a different workspace, copy that file and change the names. Your objects do not move. Lakehouse/Landing stays what it is, and only the Fabric item behind it changes.

compose.yml names a sequence you can run as one command:

compose.yml
compose:
  full:
    - build
    - load
    - test
    - health
  load-only:
    - load
    - test
    - health
  build-only:
    - build
  wipe-all:
    - wipe

Publish the Environment

From the project directory, publish before running Python work and after changing packages:

cd my-project
weaver fabric environment publish --path Environment/Weaver.Environment

Publication can take several minutes. Spark SQL needs a Lakehouse. Remote Python importing Weaver additionally needs the published Environment.

Add the example

If setup omitted the example, add its source later:

weaver add-example

This writes files only. An unchanged example can be added again; conflicting edited files are refused.

Work in a session

weaver session

Commands in the session reuse Fabric connections and Spark.

The example code

The example does not declare execution order separately. Weaver derives it from the Python imports, SQL references and shortcut declaration.

Lakehouse/Landing/Files/Sales__Customers.py
"""
Folder ID: Sales.Customers

Description: Customer records as the sales system exports them.

Lineage: Stands in for the nightly export from the sales system.

File key: "*.csv"

Incremental: false

Notes: |
  A real deployment fetches the export here, over SFTP or from an API. This one
  writes the file itself, so the project loads with nothing set up beside it.
"""

from weaver import Folder

#: The export this example stands in for.
CUSTOMERS = """\
Customer id,Customer name,Region code
C001,Harbour Freight Pty Ltd,NSW
C002,Riverside Grocers,VIC
C003,Tablelands Coffee Roasters,QLD
C004,Coastal Marine Supplies,NSW
"""


class Sales__Customers(Folder):
    def read(self):
        # Weaver supplies an empty staging directory before read() runs. This
        # method writes the export there and returns the directory.
        with self.staging_folder() as staging:
            (staging.path / "customers.csv").write_text(CUSTOMERS, encoding="utf-8")
        return staging, []

A Folder brings files in. This one writes the export itself so the example runs with nothing else set up; a real one would fetch over SFTP or from an API. Weaver creates an empty staging directory before read() runs.

Lakehouse/Landing/Tables/Sales__Customer.py
"""
Table ID: Sales.Customer

Description: One row per customer in the sales system.

Lineage: $Files/Sales.Customers

Primary key: Customer id

Comparison columns: Customer name, Region code

Schema:
  Customer id: string
  Customer name: string
  Region code: string

Notes: |
  Read from the export folder, so the table can be rebuilt from files that were
  kept.
"""

from Files.Sales__Customers import Sales__Customers

from weaver import Table


class Sales__Customer(Table):
    def read(self):
        # spark_path() is the abfss:// form Spark reads. path() is the mounted
        # pathlib.Path for ordinary Python.
        exported = Sales__Customers(self).spark_path()
        return (
            self.spark.read.option("header", True)
            .csv(exported)
            .selectExpr("`Customer id`", "`Customer name`", "`Region code`")
            .dropDuplicates(["Customer id"])
        )

A Delta table built with Spark. The import at the top, from Files.Sales__Customers import Sales__Customers, creates the dependency on the folder, so Weaver loads the folder first.

Warehouse/Curated/Sales.CustomerByRegion.sql
/*
Table ID: Sales.CustomerByRegion

Description: Customers with the name of the region they belong to.

Lineage: $Sales.Customer

Primary key: Customer id

Comparison columns: Customer name, Region name

Schema:
  Customer id: varchar(50)
  Customer name: varchar(200)
  Region name: varchar(100)

Notes: |
  Weaver reads the dependencies out of the query, so this table loads after both
  the customers and the regions it selects from.
*/

select c.[Customer id]
     , c.[Customer name]
     , r.[Region name]
  from [Sales].[Customer] c
  join [Sales].[Region] r on r.[Region code] = c.[Region code];

Ordinary T-SQL, with no Jinja, macros or ref(). Weaver reads the query and loads this table after both the customers and the regions it selects from.

Warehouse/Curated/shortcuts.yml
# A Lakehouse table, made addressable inside the Warehouse.
#
# The Warehouse cannot read Delta files; it reads the Lakehouse's SQL endpoint.
# Declaring the shortcut lets a Warehouse object select from a Lakehouse object
# while Weaver resolves the logical names to physical Fabric items.
logical:
  Warehouse/Curated/Sales.Customer: Lakehouse/Landing/Tables/Sales.Customer

A Warehouse cannot read Delta files, so this shortcut makes the Lakehouse table addressable inside it. Weaver resolves the logical names to physical Fabric items when it builds the shortcut.

Warehouse/Curated/assumptions/Sales.CustomerByRegionValid.sql
/*
Assumption ID: Sales.CustomerByRegionValid

Description: Every customer landed in a region the estate declares.

Notes: |
  A T-SQL validation compiles to a procedure anyone can run without Weaver:

      exec [_].[Assumption Sales.CustomerByRegionValid];
*/

select [Customer id]
     , [Customer name]
  from [Sales].[CustomerByRegion]
 where [Region name] is null;

An Assumption returns the rows that break a condition you are relying on, so it passes when it returns nothing. This one compiles to a stored procedure you can run without Weaver.

Build, load and test

Run these commands from the project directory. Weaver reads workspace-config.yml automatically, so you do not need to pass the workspace or item names again.

terminal
weaver build
weaver load
weaver test

  1. Build

    Build creates the schemas, folders, Delta tables, Warehouse tables and views, shortcuts and runnable load code, and records all of it in the Catalogue. It changes structure and moves no data.

  2. Load

    Weaver loads the example in dependency order: it creates the export files, loads the Delta table from them, exposes the customer table to the Warehouse through the shortcut, and then runs the Warehouse join.

  3. Test

    The two Assumptions validate the data just loaded. Weaver prints the results and records them in the Catalogue.

The generated compose.yml defines a sequence that runs all three in one session:

terminal
weaver compose full

In a notebook

The same operations are available as Python functions and use the same project configuration:

notebook cell
import weaver

weaver.build()
weaver.load()
weaver.test()

Estate health

Once everything is installed and loaded, check where the estate stands:

terminal
weaver health

The dependency graph

The example does not contain a separate execution-order definition. Weaver derives one dependency graph from the Python imports, SQL references and shortcut declaration. It includes files, tables, shortcuts, Warehouse SQL and validations.

Weaver uses the dependency graph to determine load order, identify the objects affected by a rebuild, and check whether objects are behind their sources.

Troubleshooting

weaver doctor --workspace Analytics

Doctor checks this machine and identity against the named workspace from any directory. It reads no project configuration and needs no Catalogue or Environment.

Authentication                     OK
  Azure CLI
Fabric REST                        OK
  7 workspaces visible
Workspace Analytics                OK
OneLake                            OK
  via Lakehouse/Landing
Warehouse TDS                      OK
  via Warehouse/Curated
Fabric Spark / Livy                OK
  via Lakehouse/Landing

Doctor discovers one Lakehouse and Warehouse for its probes. A missing item is MISSING, a rejected probe is FAILED and a transport or runtime failure is ERROR. Missing probe items do not fail the command. Spark startup can take a minute.

Use weaver check for repository errors and weaver health for installed state.
