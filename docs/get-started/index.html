Run Weaver on a small Fabric estate

The Sales example gives you a Lakehouse table, a Warehouse table, a shortcut between them and two checks. Weaver builds, loads and tests the chain in your own workspace.

Before you begin

  • A Microsoft Fabric workspace on a running capacity. You need permission to use its existing items or create the ones you name.
  • Python 3.11 or later when working from your own machine. Fabric notebooks already provide Python.
  • A Fabric sign-in. The desktop CLI can use Azure CLI credentials, a configured service principal or Microsoft sign-in in a browser.

If you are working from your own machine, this checks the sign-in and the workspace before setup:

terminal
pip install weaverstack
weaver doctor --workspace Analytics

Initialise the project

The shortest path is the desktop wizard. It asks for a project folder, a Catalogue Warehouse, an Environment and at least one destination item. Choose the Sales example when prompted.

terminal
weaver initialise --workspace Analytics

initialise writes the project and creates or reuses the Catalogue, Environment, Lakehouse and Warehouse you select. It does not build the project or load data.

Supply every choice

For a repeatable setup, name the project folder and Fabric items explicitly. --non-interactive refuses missing input or authorisation rather than opening a prompt or browser.

terminal
weaver initialise --workspace Analytics \
  --project-folder ./Analytics \
  --catalogue Catalogue \
  --environment Weaver \
  --lakehouse Landing \
  --warehouse Curated \
  --example --non-interactive

Or start inside Fabric

The Python package exposes the same operations in a Fabric notebook. The notebook supplies the workspace it is already running in.

notebook cell
%pip install weaverstack
notebook cell
from pathlib import Path
import weaver

project_folder = Path("builtin") / "Analytics"
weaver.initialise(
    project_folder,
    catalogue="Catalogue",
    environment="Weaver",
    lakehouse="Landing",
    warehouse="Curated",
    example=True,
)

Look at what Weaver wrote

The project keeps each object under the logical Fabric item that owns it. Python imports, SQL references and shortcut declarations provide the dependencies.

Analytics/
README.md
workspace-config.yml
workflow.yml
Environment/Weaver.Environment/

Lakehouse/Landing/
├── Files/
│   └── Sales__Customers.py
├── Tables/
│   └── Sales__Customer.py
└── assumptions/
    └── Sales__CustomerValid.py

Warehouse/Curated/
├── shortcuts.yml
├── Sales.Region.sql
├── Sales.CustomerByRegion.sql
└── assumptions/
    └── Sales.CustomerByRegionValid.sql

The workspace configuration carries the physical bindings:

workspace-config.yml
workspace: Analytics
environment: Weaver
catalogue: Warehouse/Catalogue

targets:
  Lakehouse/Landing: Landing
  Warehouse/Curated: Curated

Copy that file and change the physical names to use the same project in another workspace. The source still refers to Lakehouse/Landing and Warehouse/Curated.

Publish, then run

The generated Environment carries Weaver and the Python packages used by your project. Publish it before the first Python load and after changing its packages.

terminal
cd Analytics
weaver fabric environment publish --path Environment/Weaver.Environment
weaver workflow full

The generated full workflow runs build, load, test and health in one session. Build creates the Fabric structure; load runs the data work in dependency order; test runs the two checks; health reports whether the installed estate is current.

You can run the stages separately when that is the point:

terminal
weaver build
weaver load
weaver test
weaver health

One run, one graph and durable state

The item boundary disappeared from orchestration

The Warehouse join waited for the Lakehouse table because Weaver read both into one graph. You did not write a second pipeline to coordinate the two engines.

The run left state behind

The Catalogue now holds the installed graph, load positions and current outcomes. A later command starts from that state rather than rediscovering it from logs.
