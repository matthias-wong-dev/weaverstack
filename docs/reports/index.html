One Report project, correctly bound in each environment.

Keep the native Report in source control. Weaver resolves its destination and verifies its link to the intended deployed semantic model.

A different workspace should not mean a different Report

Publishing copies for development and production leaves another connection to check by hand. Keep the native definition.pbir association and select the destination through configuration:

Development

workspace-dev.yml 
workspace: Parcel BI Development
targets:
  SemanticModel/Parcel: Parcel_Dev
  Report/Parcel: Parcel_Report_Dev

Production

workspace-prod.yml 
workspace: Parcel BI Production
targets:
  SemanticModel/Parcel: Parcel
  Report/Parcel: Parcel_Report

Build deploys and verifies the selected model first, then the Report and its actual binding. The service IDs belong in the deployed payload, not edits to your local project.

Verify the destination, not just the item name

The Report in development must point to the development model; the production Report must point to the production model and workspace. Use the same native files for both Builds, then check those bindings and open the resulting Report.

Deploy the same source to development and production →

Keep refresh with the model

The Report displays its semantic model’s data. Refresh and validate that model; there is no separate Report data Load or Test. In a catalogue-backed estate, an already certified model can also support a Report-only update.
