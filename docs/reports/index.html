One report project. Development and production without the publishing ritual.

Keep the native project. Choose the workspace, name and linked model at deployment.

Keep the same native project

Repeated publishing can leave you with renamed copies, duplicate files and another model connection to check. Keep one native report project in source control and choose its target through configuration.

Works with Power BI alone. Integrates with Fabric when needed. You still need the appropriate service licence, workspace access and deployment permissions.

Development

workspace-dev.yml 
workspace: Parcel BI Development
targets:
  SemanticModel/Parcel: Parcel_Dev
  Report/Parcel: Parcel_Report_Dev

Production

workspace-prod.yml 
workspace: Parcel BI Production
targets:
  SemanticModel/Parcel: Parcel
  Report/Parcel: Parcel_Report

The workspaces already exist. The project files are the same in both configurations.

The linked report follows its model

A Report linked to a model in the project uses that model’s resolved target. The deployment payload changes, not the authored source files. The selected model is deployed and verified before linked Reports, and the Report binding is checked afterwards.

A Report has a definition, not a data-load step. Refresh its model. An unrelated authored byConnection binding remains as authored; Weaver does not automatically reverse-map it to another model.

Update the report without making another copy

Catalogue-backed Report-only builds can reuse a certified linked model and skip unchanged Report work. A catalogue-free selection redeploys and verifies; selecting only a project-linked Report is not a substitute for deploying or certifying its model under the supported rules.
