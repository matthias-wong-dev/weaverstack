Why Weaver

Fabric-native

Weaver is built for Microsoft Fabric alone. It models Lakehouses, Warehouses, OneLake, Spark, T-SQL, shortcuts and Fabric Environments directly.

Natural development

Write Python and T-SQL as you normally would. Weaver derives dependencies from your imports and SQL references.

Ready for scale

Weaver keeps one dependency graph across the whole estate, builds only what changed, and records each object's load position between runs.

Free and open source

Free and open source, forever. Weaver is licensed under the Mozilla Public License 2.0, with no Weaver subscription or hosted service required.

What a Weaver project looks like

This is the Sales example weaver initialise can write for you. A folder of exported customers, a Delta table built from it, a Warehouse table joining those customers to regions, and a check on each side.

my-project/
workspace-config.yml
compose.yml

Lakehouse/Landing/
├── Files/
│   └── Sales__Customers.py
├── Tables/
│   └── Sales__Customer.py
└── assumptions/
    └── Sales__CustomerValid.py

Warehouse/Curated/
├── shortcuts.yml
├── Sales.Region.sql
├── Sales.CustomerByRegion.sql
└── assumptions/
    └── Sales.CustomerByRegionValid.sql

Each file sits under the Fabric item that owns it. Weaver derives execution order from the dependencies in the Python and SQL.

The dependency graph

Weaver derives the graph from the source files. The Python table depends on the export folder; the Warehouse join depends on the customer shortcut and a local region table; each validation depends on its target.

Get started

One install gives you the library and the weaver command. The same package runs in a Fabric notebook and on your own machine.

terminal
pip install weaverstack
weaver initialise my-project

Review the workspace and item choices, then select the Sales example to generate its source. From my-project, publish the Environment and run weaver compose full to build, load, test and check health.
