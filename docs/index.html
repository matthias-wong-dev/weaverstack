Microsoft Fabric, made easier.

Weaver helps you build and operate data pipelines across Microsoft Fabric from one repository. You write normal Python and T-SQL. Weaver works out what depends on what, builds it into your Lakehouses and Warehouses, and keeps track of what has run.

Why Weaver

Fabric-native

Built specifically for Microsoft Fabric. Lakehouses, Warehouses, OneLake, Spark, T-SQL, shortcuts and Fabric Environments are the things Weaver models, not things it works around.

Natural development

Write normal Python and normal T-SQL. Weaver reads your Python imports and the relations your SQL selects from, and builds the dependency graph out of what is already there.

Ready for scale

One graph across every object in the estate, incremental builds, cross-item dependencies, and operational state that survives between runs.

Free and open source

Free and open source, forever. Weaver is licensed under the Mozilla Public License 2.0. There is no paid Weaver service, no hosted tier and no per-user charge.

What a Weaver project looks like

This is the Sales example weaver initialise can write for you, as it comes out. A folder of exported customers, a Delta table built from it, a Warehouse table that joins customers to regions, and a check on each side.

my-project/
workspace-config.yml
compose.yml

Lakehouse/Landing/
├── Files/
│   └── Sales__Customers.py
├── Tables/
│   └── Sales__Customer.py
└── assumptions/
    └── Sales__CustomerValid.py

Warehouse/Curated/
├── shortcuts.yml
├── Sales.Region.sql
├── Sales.CustomerByRegion.sql
└── assumptions/
    └── Sales.CustomerByRegionValid.sql

Each file sits under the Fabric item that owns it. Nothing in a file says what runs before it, and nothing has to.

And here is what Weaver sees

Weaver reads those files and works out the whole graph: the Python table reads the export folder, the Warehouse join reads the customers through a shortcut and the regions from its own table, and each check hangs off the thing it checks.
