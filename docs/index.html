Microsoft Fabric, made easier.

Weaver brings your Lakehouse and Warehouse work into one repository, and you keep writing Python and T-SQL as you already do. It reads your code to work out what depends on what, builds the Fabric objects, and keeps track of what has run.

Why Weaver

Fabric-native

Weaver is built for Microsoft Fabric alone. It models Lakehouses, Warehouses, OneLake, Spark, T-SQL, shortcuts and Fabric Environments directly.

Natural development

Write Python and T-SQL as you normally would. Weaver works out the dependencies from your imports and your SQL references.

Ready for scale

Weaver keeps one dependency graph across the whole estate, builds only what changed, and remembers how far each object got between runs.

Free and open source

Free and open source, forever. Weaver is licensed under the Mozilla Public License 2.0, with no Weaver subscription or hosted service required.

What a Weaver project looks like

This is the Sales example weaver initialise can write for you. A folder of exported customers, a Delta table built from it, a Warehouse table joining those customers to regions, and a check on each side.

my-project/
workspace-config.yml
compose.yml

Lakehouse/Landing/
├── Files/
│   └── Sales__Customers.py
├── Tables/
│   └── Sales__Customer.py
└── assumptions/
    └── Sales__CustomerValid.py

Warehouse/Curated/
├── shortcuts.yml
├── Sales.Region.sql
├── Sales.CustomerByRegion.sql
└── assumptions/
    └── Sales.CustomerByRegionValid.sql

Each file sits under the Fabric item that owns it. Weaver derives execution order from the dependencies in the Python and SQL.

The dependency graph

Weaver reads the files and works the graph out for you. The Python table reads the export folder, the Warehouse join reads those customers through a shortcut and its regions from a local table, and each check hangs off whatever it validates.
