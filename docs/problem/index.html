The problem

Building one thing in Fabric is straightforward

Fabric makes it straightforward to work with individual Lakehouses, Warehouses, notebooks and SQL workloads. The complexity appears when those parts need to operate together as a production data platform.

Part one

Fabric starts simple

Fabric already provides strong execution engines.

You create a Lakehouse, land a file in it, then read that file with Spark in a notebook and write a Delta table. A Warehouse gives you T-SQL over the same estate. Each of these steps is well documented and works on its own.

Each step uses a capable tool, and the pipeline works as long as somebody runs the steps in the right order.

Part two

The pieces have to work together

The complexity appears at the boundaries between Fabric components.

Two engines, two languages

The Lakehouse runs Spark and Python while the Warehouse runs T-SQL. Both belong to the same pipeline, but their dependency graphs are separate, so execution order has to be maintained by hand.

Several Fabric items

Most estates hold several Lakehouses and Warehouses. A dependency that crosses between two items is no different in principle from one inside a single item, but Fabric does not treat it the same way.

Shortcuts

A Warehouse cannot read Delta files directly, so it reads a Lakehouse through its SQL endpoint using a shortcut. That shortcut is usually configured outside the pipeline code that depends on it.

Environments

Spark code needs libraries, which come from a Fabric Environment. The Environment, its published state and its library versions all have to stay aligned with the code that assumes them.

Logical against physical

Development and production Lakehouses are separate Fabric items with different names, so something has to resolve which physical item a given piece of code refers to.

Source control

Notebooks, SQL scripts, pipeline definitions, shortcut configuration and item settings are stored separately and versioned at different rates, which makes a single platform change hard to review as one unit.

Fabric provides these capabilities separately, while a production pipeline needs to coordinate them as one system.

Part three

A pipeline becomes a production system

As a pipeline moves into regular production, it needs to keep track of more than whether the latest run succeeded.

Once the same pipeline runs every night against data that arrives on its own schedule, it has to answer questions like these:

  • How much needs reloading? Reading the whole source every night stops being practical as volumes grow, so the pipeline needs to know how far it got last time.
  • What is the current state? Which objects are up to date, which are behind their sources and which have not run at all.
  • What happens after a failure? Which objects succeeded, which were blocked by the failure, and which can safely be retried.
  • Is this table still current? A table can load successfully and still be stale, because a table it reads from loaded again afterwards.
  • What does this column mean? Descriptions, keys, foreign keys and lineage become necessary as soon as somebody other than the author maintains the pipeline.
  • Is the data correct? Whether the query ran is a different question from whether the result means what it is supposed to.

Each of these needs state that persists between runs. A pipeline that only knows about its current invocation cannot answer them.

Part four

Operational data handling

Production pipelines also need consistent handling for incremental state, rejected rows, unexpected changes and partial failures. These are usually built by hand in each organisation.

Incremental position

A bookmark records how far the last clean load reached, along with rules for when it may advance. Advancing it after a partial run silently skips data, which is a failure that can go unnoticed for a long time.

Changed rows

A load needs to know which rows are new, which changed and which are gone. Absence means something different when the source sends a full extract than when it sends today's batch.

Duplicate keys

When a source sends the same key twice, the pipeline needs a policy: fail the load, keep one row, or set the duplicates aside and continue. That policy has to be recorded somewhere the pipeline can read it.

Null violations

Detecting a null in a column that should not allow one is straightforward. Deciding what the load does with the offending row is the part that needs designing.

Rejected rows

Rows that a load refuses need to be stored somewhere along with the reason, so they can be reviewed later.

Unexpectedly large changes

A short extract can produce a load that deletes most of a table without anything being technically wrong. Stability thresholds can stop unexpectedly large deletes or updates before they are applied.

Load statistics

Insert, update and delete counts recorded as data, so they can be read back and compared across runs.

Continuing after a failure

When one source is unavailable, the rest of the estate often has no dependency on it. A run should be able to continue on independent branches while blocking anything downstream of the failure.

These requirements are long established in data engineering. What changes with Fabric is that they have to be assembled across two execution engines and several items, on a platform that supplies the engines and leaves the coordination to you.

Where Weaver comes in

Weaver does not replace anything in Fabric. Delta tables remain Delta tables, Warehouses remain Warehouses, and Spark runs on Fabric Spark.

What Weaver adds is coordination and persistent state. One repository describes the whole estate, and one dependency graph covers every object in it regardless of which engine runs it or which item holds it. The Catalogue records what is installed, how far each object has loaded and what happened on the way. The operational behaviours above become declarations rather than code you write again for each project.
