The problem

The hard part begins between the Fabric items

A Lakehouse table or Warehouse query can be straightforward on its own. The engineering burden appears when files, Python, Delta, shortcuts and T-SQL have to behave as one system across environments and across runs.

The data path is one chain

FilesLakehouse
→
PythonSpark
→
DeltaLakehouse table
→
Shortcutitem boundary
→
T-SQLWarehouse

Fabric exposes capable surfaces for each step. It does not give the whole chain one dependency model. Without one, execution order is repeated in pipelines, triggers or local conventions, especially where the engine or Fabric item changes.

The dependency is still a dependency when it crosses from Python to T-SQL or from one Fabric item to another. Only the coordination becomes harder.

The estate exists in more than one environment

Development and production usually contain the same logical objects under different physical Fabric item names.

References drift into deployment detail

If object code names physical Lakehouses and Warehouses, moving between workspaces means rewriting references or carrying environment logic through the source.

Structure and data move on different clocks

Schemas, tables, views, shortcuts and Environment packages change independently from source data. Coupling deployment to loading turns a structural change into a data event.

The more Fabric items an estate gains, the more places there are to keep bindings, structure and execution order in agreement.

A run ending is not the same as the estate being current

Production work carries state between runs. Logs tell you what was printed; they do not by themselves tell the next run what remains safe to do.

Incremental position

Each load needs a trustworthy point to continue from. Advancing it after a partial run risks skipped data; losing it turns recovery into a full reload.

Partial failure

Some objects succeed, one fails, its descendants are blocked, and independent branches may still finish. Recovery depends on knowing which condition applies to each object.

Staleness

A table can have succeeded yesterday and still be behind its sources today. Current state depends on both run outcomes and the dependency graph.

Validation

A completed query establishes that code ran, not that its output is acceptable. Validation results have to remain attached to the objects they describe.

Weaver removes the parallel model

The project supplies the objects and their dependencies. Workspace configuration supplies the physical bindings. The Catalogue carries installed and operational state. Weaver uses the three together for build, load, test and health.

  • One dependency graph crosses Lakehouses, Warehouses and engines.
  • Logical object references stay the same between environments.
  • Build deploys structure without forcing data movement.
  • Loads leave bookmarks and outcomes for recovery and health.

Weaver replaces those separate descriptions with one model to reconcile when the estate changes.
