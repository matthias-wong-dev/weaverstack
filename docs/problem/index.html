The problem

Building one thing in Fabric is straightforward

Fabric makes it straightforward to work with a Lakehouse, a Warehouse, a notebook or a SQL workload on its own. It gets harder once you need all of them running together as one production platform.

Fabric starts simple

You create a Lakehouse, land a file in it, then read that file with Spark in a notebook and write a Delta table. A Warehouse gives you T-SQL over the same estate. Each step is documented, and each one works on its own.

Fabric does not provide one dependency model across these components, so their execution order must be coordinated separately.

Coordinating Fabric components

The complexity starts when those components form one pipeline.

Two engines, two languages

Your Lakehouse runs Spark and Python; your Warehouse runs T-SQL. Fabric has separate dependency graphs for the two engines, so their execution order requires separate coordination.

Several Fabric items

Most estates hold several Lakehouses and Warehouses. A table in one item can depend on a table in another exactly as it would on a local one, but Fabric does not treat the two cases the same way.

Shortcuts

A Warehouse cannot read Delta files, so it reaches a Lakehouse through a shortcut to its SQL endpoint. You usually configure that shortcut somewhere other than the pipeline code that relies on it.

Environments

Your Spark code needs libraries, and those come from a Fabric Environment. You then have to keep the right Environment published, with the right versions in it, matching whatever the code assumes.

Logical against physical

Your development Lakehouse and your production Lakehouse are separate Fabric items with different names. Each logical code reference must be resolved to the correct physical item for its environment.

Source control

Notebooks, SQL scripts, pipeline definitions, shortcut configuration and item settings all live in different places and version at different rates. One change to the platform touches several of them, and you review them separately.

Fabric's breadth and the freedom to combine its components can create dependencies and operating conventions spread across Lakehouses, Warehouses, notebooks, shortcuts, Environments and orchestration as an estate grows.

A pipeline becomes a production system

Production pipelines require durable operational state across runs.

  • Incremental position. Reading a full source on every run becomes impractical as volumes grow. A bookmark records how far each object processed.
  • Current operational state. Current state distinguishes objects that are up to date, behind their sources or never loaded.
  • Recovery after failure. Weaver records which objects succeeded, failed or were blocked, and which can be retried.
  • Staleness relative to dependencies. A table can load successfully and become stale when an upstream object loads again.
  • Metadata and lineage. Descriptions, keys, foreign keys and lineage identify an object's meaning and dependencies.
  • Validation state. A completed query does not establish that its output is valid.

Operational data handling

Incremental state, rejected rows, stability controls and partial failures need a consistent operating model across the estate.

Incremental position

A bookmark records the position of the last clean load and advances only when processing completes successfully. Advancing it after a partial load can leave data permanently unprocessed.

Changed rows

A load has to tell new rows from changed ones, and both from rows that have gone. A missing key means something different when the source sends you everything than when it sends today's batch.

Duplicate keys

Duplicate primary and unique keys are refused and set aside with a reason. A consistent policy prevents different loads from handling the same data condition differently.

Null violations

Null violations need a defined load policy. Weaver rejects and records rows with nulls in columns declared not null.

Rejected rows

Rejected rows are persisted with their rejection reason for investigation and recovery.

Unexpectedly large changes

A load can be structurally valid while representing an implausibly large change. Stability thresholds can stop the change before it is applied.

Load statistics

Weaver records inserted, updated and deleted row counts for each load so they can be compared across runs.

Continuing after a failure

Independent branches can continue after a failure, while descendants of the failed object remain blocked.

Fabric spreads these concerns across multiple engines and items, which makes a common operating model more valuable as the estate grows.

Where Weaver comes in

Weaver coordinates Fabric's existing data-engineering surfaces through one repository, dependency graph and Catalogue.

The repository defines dependencies and logical-to-physical bindings across Fabric items. The Catalogue records installed state, bookmarks, load and test outcomes, and operational history. Execution remains on Fabric's native engines.
