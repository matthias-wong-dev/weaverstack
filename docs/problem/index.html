The problem

Fabric gives you the pieces. Keeping them together is the hard part.

A Lakehouse table or Warehouse query can be simple on its own. Keeping files, Python, Delta, shortcuts and T-SQL in sync gets harder as the project grows.

The repetition starts before the estate is large

One developer with two spreadsheets still has a repeatability problem. A Power BI project can accumulate publishing copies, manual renaming and model bindings to check in development and production.

Weaver adds project organisation and environment configuration without replacing the languages or native definitions. Destination naming, supported source mapping and source credentials remain separate controls.

Fabric has good tools for each step. The Warehouse query still has to wait for the Lakehouse table, and the Lakehouse table still has to wait for the files. Someone has to keep that order correct.

Without Weaver, the same dependencies often appear again in pipelines, triggers or local conventions.

Development and production add another set of names

The source project is the same in development and production, but real Lakehouses, Warehouses, models and Reports can have different names and workspaces.

References need to point to the right place

Hard-code the Fabric item names and the source changes between environments. Put the mapping elsewhere and that mapping has to remain clear and reviewable.

Fabric objects and data change separately

A new table, column or shortcut may need to be deployed before its data is ready to load. Treating both as one job makes every structural change harder to control.

One failed object leaves several questions

What finished?

A run may load several tables before one fails. Rerunning everything wastes time and may repeat work that already completed.

What can still run?

The failed object's dependants must wait, but an independent branch may be safe to continue.

Where should the next load resume?

Each incremental load needs a trustworthy position. Moving it after a partial run can skip data; losing it forces the load to start again.

What is now stale?

A downstream table can have succeeded yesterday and still be out of date after an upstream table loads today.

Weaver keeps the answers with the project

  • It uses Python imports, supported T-SQL references, explicit Spark SQL dependencies and shortcut declarations.
  • It maps the same project names to the right Fabric items in each environment.
  • It creates or changes Fabric objects separately from loading their data.
  • It records what loaded, failed or was blocked, and where each load should continue.

You maintain the Python, SQL and Fabric choices. Weaver handles the repeated work of keeping them in order.
