The problem

Building one thing in Fabric is straightforward

Fabric makes it straightforward to work with a Lakehouse, a Warehouse, a notebook or a SQL workload on its own. It gets harder once you need all of them running together as one production platform.

Part one

Fabric starts simple

The engines are all there and they work.

You create a Lakehouse, land a file in it, then read that file with Spark in a notebook and write a Delta table. A Warehouse gives you T-SQL over the same estate. Each step is documented, and each one works on its own.

The pipeline works, as long as somebody runs the steps in the right order.

Part two

The pieces have to work together

The trouble starts at the boundaries between them.

Two engines, two languages

Your Lakehouse runs Spark and Python; your Warehouse runs T-SQL. They belong to the same pipeline, but Fabric keeps their dependency graphs apart, so you maintain the running order yourself.

Several Fabric items

Most estates hold several Lakehouses and Warehouses. A table in one item can depend on a table in another exactly as it would on a local one, but Fabric does not treat the two cases the same way.

Shortcuts

A Warehouse cannot read Delta files, so it reaches a Lakehouse through a shortcut to its SQL endpoint. You usually configure that shortcut somewhere other than the pipeline code that relies on it.

Environments

Your Spark code needs libraries, and those come from a Fabric Environment. You then have to keep the right Environment published, with the right versions in it, matching whatever the code assumes.

Logical against physical

Your development Lakehouse and your production Lakehouse are separate Fabric items with different names. Something has to know which one a given piece of code means today.

Source control

Notebooks, SQL scripts, pipeline definitions, shortcut configuration and item settings all live in different places and version at different rates. One change to the platform touches several of them, and you review them separately.

Fabric hands you each of these separately. A production pipeline has to run them as one system.

Part three

A pipeline becomes a production system

Once a pipeline runs every night, you need to know more than whether last night worked.

The data arrives on its own schedule, and you start needing answers to questions like these:

  • How much do you reload? Reading the whole source every night stops being practical as volumes grow, so the pipeline has to remember how far it got last time.
  • Where does the estate stand? Which objects are up to date, which are behind their sources, and which never ran.
  • What happens after a failure? Which objects succeeded, which the failure blocked, and which you can safely retry.
  • Is this table still current? It can load perfectly well and still be stale, because something it reads loaded again afterwards.
  • What does this column mean? You need descriptions, keys, foreign keys and lineage as soon as somebody other than the author picks the pipeline up.
  • Is the data right? Whether the query ran is a different question from whether the answer means what you think it does.

Answering any of these means keeping something between runs. A pipeline that only knows about the run it is in cannot tell you.

Part four

Operational data handling

You also need consistent handling for incremental state, rejected rows, unexpected changes and partial failures. Most teams build all of this by hand, and most teams build it more than once.

Incremental position

A bookmark records how far the last clean load reached, and you need rules for when it moves. Advance it after a partial run and you skip data silently, which nobody notices for a while.

Changed rows

A load has to tell new rows from changed ones, and both from rows that have gone. A missing key means something different when the source sends you everything than when it sends today's batch.

Duplicate keys

The source sends you the same customer twice. You decide whether to fail the load, keep one row, or set both aside and carry on, and then you write that decision down somewhere the pipeline can read it.

Null violations

Spotting a null where you do not allow one is easy. Deciding what the load then does with that row is the part you have to design.

Rejected rows

Once a load starts refusing rows, they have to go somewhere, with the reason attached, so somebody can look at them tomorrow.

Unexpectedly large changes

The source comes in short and the load is about to delete most of a table. Nothing is technically wrong, so you want a threshold that stops the delete before it lands.

Load statistics

How many rows were inserted, updated and deleted, kept as data you can read back later and compare across runs.

Continuing after a failure

One source is down, and half the estate has nothing to do with it. You want the run to carry on down the branches that do not touch it, and stop everything that does.

Data engineering has needed all of this for a long time. What Fabric changes is that you now assemble it across two engines and several items, on a platform that gives you the engines and leaves the rest to you.

Where Weaver comes in

Weaver replaces none of it. Your Delta tables are still Delta tables, your Warehouse is still a Warehouse, and your Spark still runs on Fabric Spark.

What Weaver adds is the coordination and the memory. You describe the whole estate in one repository, and Weaver builds one dependency graph across it, whichever engine runs an object and whichever item holds it. It records what is installed, how far each object has loaded and what happened along the way. Everything in the list above you declare once, instead of writing it again for every project.
