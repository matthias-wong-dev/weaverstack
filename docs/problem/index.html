The problem

Building one thing in Fabric is straightforward

Coordinating a whole data platform is harder. This page walks through where that difficulty actually comes from. It starts with things you will recognise from your first week in Fabric, and ends with the parts that only show up once real data is flowing.

Part one

Fabric really does start simple

The engines are good. That is not the problem.

You make a Lakehouse. You drop a file in it. You open a notebook, read the file with Spark, write a Delta table. You make a Warehouse and write some T-SQL. Every one of those steps is well documented and works the first time.

Four steps, four good tools. If that were the whole job, you would not need Weaver and this page would be shorter.

Part two

Then the pieces have to work together

The difficulty is not in any one Fabric feature. It is in the joins between them.

Here is what starts to accumulate:

Two engines, two languages

The Lakehouse is Spark and Python. The Warehouse is T-SQL. Both belong in the same pipeline, and nothing joins their dependency graphs. What runs first is something you have to know and remember.

Several Fabric items

Real estates have more than one Lakehouse and more than one Warehouse. A dependency that crosses between them is the same kind of dependency as one that does not, but it is not treated as one.

Shortcuts

A Warehouse cannot read Delta files. It reads a Lakehouse's SQL endpoint through a shortcut. That is a real constraint, and it usually becomes a configuration task that lives somewhere other than your pipeline code.

Environments

Spark code needs libraries. Libraries come from a Fabric Environment. Which Environment, published when, containing what version, is another thing to keep aligned with the code that assumes it.

Logical against physical

Your development Lakehouse and your production Lakehouse are different Fabric items with different names. Something has to know which one a given piece of code means, today.

Source control

Notebooks, SQL scripts, pipeline definitions, shortcut configuration and item settings live in different places and version at different rates. Reviewing a change to the platform means reviewing several of them at once.

The complexity comes from coordination, not from any one Fabric feature.

None of this is a criticism of Fabric. A platform that gives you a Lakehouse, a Warehouse, Spark, T-SQL, OneLake and shortcuts is giving you a lot. But it gives them to you as separate things, and a data platform is one thing.

Part three

A pipeline becomes a production system

The hard parts show up after the first successful run.

The first run is a demo. The hundredth run is a system, and a system has questions the demo never asked.

Once the same pipeline runs every night, on data that arrives on its own schedule, you start needing answers to things like:

  • How much do I reload? Reading the whole source every night stops being sensible somewhere around the point it starts taking hours. So the pipeline needs to know how far it got last time.
  • What happened last night? Not the log file. The current state: which objects are up to date, which are behind, which have not run at all.
  • Something failed. Now what? What succeeded, what did not run because of it, what should be retried, and what must not be retried because it half-ran.
  • Is this table still trustworthy? It loaded fine, but the table it reads from loaded again afterwards. Being successful and being current are different things.
  • What is this column? Descriptions, keys, foreign keys and lineage stop being nice-to-have the moment somebody other than the author has to work on it.
  • Is the data right? Not "did the query run" but "does the result mean what we think it means".

Every one of those needs somewhere to keep an answer between runs. A pipeline that only knows what happened during the current invocation cannot answer any of them.

Part four

And then the properly awkward parts

These are the ones people build by hand, again, in every organisation. They are not glamorous and they are not optional.

Knowing how far you got

A bookmark that says where the last clean load reached, and rules about when it is allowed to move. Advance it after a run that half-worked and you will silently skip data. Advancing too eagerly is the failure mode nobody notices for a month.

Rows that change, not just rows that arrive

Which rows are new, which changed, which disappeared, and what "disappeared" even means when your source only sent you today's batch.

Duplicate keys

The source sent you the same customer twice. Do you fail the load, take one arbitrarily, or set both aside and carry on? Somebody has to decide, and the decision has to be written down somewhere the pipeline can read.

Nulls where there should not be nulls

Same question, different shape. Detecting it is easy. Deciding what the pipeline does about it is the actual work.

Rejected rows

Once you decide to set bad rows aside, they have to go somewhere, with the reason, so somebody can look at them tomorrow.

Changes that are too big

The load is about to delete 80% of a table. Nothing is technically wrong: the source just came in short. A pipeline that does not notice this is a pipeline that will one day empty a table on a Sunday.

Load statistics

How many rows were inserted, updated and deleted. Not as a log line, but as a number you can read later and compare.

Carrying on after a failure

One source is down. Half the estate has nothing to do with it. A nightly run that stops dead at the first problem wastes a night; one that ploughs on regardless corrupts things downstream.

Making Fabric easier also means making the hard parts boring.

None of this is exotic. It is what data engineering has needed for thirty years. What changes with Fabric is that you now have to assemble it yourself, across two engines and several items, on top of a platform that gives you the engines and leaves the assembly to you.

Where Weaver comes in

Weaver does not replace anything in Fabric. Your Delta tables are Delta tables, your Warehouse is a Warehouse, your Spark runs on Fabric Spark.

What Weaver adds is the coordination and the memory. One repository describing the whole estate. One dependency graph across every object in it, regardless of which engine runs it or which item holds it. One place recording what is installed, how far each thing has loaded, and what happened. And sensible, declarable answers to the awkward parts, so you are configuring them rather than writing them again.

Fabric already provides the engines. Weaver makes them easier to engineer as one data platform.
