Sophisticated semantic models. A familiar way to build them.

Start with the Power BI project you have. Add standards, checks or model variants when they solve a real problem.

Deploy the model you already have

Works with Power BI alone. Integrates with Fabric when needed. The standalone route needs an appropriate Power BI service licence, workspace access and permissions. It does not need a catalogue Warehouse, Lakehouse, Spark session or Fabric Environment.

Keep your native PBIP/TMDL project and ordinary modelling. A small workspace configuration chooses the destination; Build deploys the model and linked Report.

Deploy an existing Power BI project →

One model, different environments

Keep one source definition. Development and production configurations choose the workspace and physical model name. A Report linked to the model follows its resolved deployment target.

Target naming is separate from mapping supported shared source expressions and granting source credentials. Weaver is not a global replacement engine for arbitrary M expressions.

Use development and production targets →

Apply one convention with a native annotation

Hide many-side relationship keys with one annotation in the optional model overlay:

PowerBI/Parcel/Parcel.tmdl 
model Model
    annotation 'Weaver.AutoHideForeignKeys' = true

The model needs an actual relationship for the rule to have an effect. Keep the rest of its native definition.

Share formatting and calculation structures through native TMDL policy. Add a small Python annotation only when a convention needs a transformation native declarations cannot express.

Test what the model says

DAX Assumptions can check a standalone model without a catalogue. When a supported Warehouse or Lakehouse source is available, compare the model’s DAX result with independently calculated SQL.

These checks test the assumptions you wrote. They do not guarantee that every report visual is correct.

Validate a semantic model →

Connect to a larger Fabric estate when needed

Add catalogue registration and managed sources for recorded lineage, installed dependency ordering, model refresh state and persistent validation results. The graph covers the managed or registered estate, not automatic discovery of every unmanaged workspace item.

Connect a model to a Fabric estate →

One foundation, several model variants

Reuse base definitions, then add, exclude or override content for different audiences. Ordinary deployment does not require composition, and a source base need not be deployed just because a variant uses it.

Hiding or excluding objects is not a security policy. Validate RLS, OLS and service permissions separately.

Compose model variants →

Authored definitions and deployed models remain native. Weaver annotations run in Weaver, not automatically in Power BI Desktop. Native output does not imply a compiled-TMDL download or lossless bidirectional Desktop round-tripping.
