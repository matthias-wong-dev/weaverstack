Weaver vs dbt

dbt is a transformation framework. Weaver covers the wider operational lifecycle of data engineering on Microsoft Fabric: physical structure, loading, operational state and dependencies that cross Fabric items.

Four main differences

Fabric-native

dbt reaches Fabric through adapters. Weaver models Lakehouses, Warehouses, OneLake, shortcuts, Fabric Environments, Spark and T-SQL directly.

A dbt project runs against one adapter and one connection, so your Lakehouse and your Warehouse are separate targets and no single graph spans them. In Weaver they are two items in the same graph.

Natural development

In dbt you declare dependencies with ref() and source(). Weaver reads them out of your Python imports and your SQL references.

So you write Python as Python and T-SQL as T-SQL, and the graph follows the code instead of a second set of declarations you keep in step with it.

Build and load are separate

In dbt, materialising a model and populating it are the same act. Weaver splits them into two commands.

That lets you install a whole platform's structure into a fresh workspace before loading anything, or deploy a schema change without moving a row.

Operational state is first class

Weaver keeps each object's installed and operational state inside Fabric: how far it loaded, whether its checks passed, and what the last load changed.

dbt writes run artifacts such as the manifest and run results, and selects on state by comparing against a previous manifest. Weaver keeps that state in the data platform, where the next command reads it directly.

Mature data engineering is more than transformation

Transformation is the most visible part of data engineering, and the part most worth getting right. A production pipeline also has physical structure to deploy, state to carry between runs, bad rows to deal with and failures to survive.

Physical structure

Before any data moves, something has to exist: Lakehouses, Warehouses, schemas, folders, tables, views, shortcuts, and the Environment your Spark code takes its libraries from. You create, alter and occasionally rebuild all of that on a rhythm that has little to do with how often data arrives.

Deploy structure and data together and every structural change becomes a data event. Add a column and you reload. Deploy to a fresh workspace and you have to load it before you can see whether the shape is right.

Weaver splits them. Build makes Fabric match your repository, load moves the data, and on a large estate you often want one without the other.

Operational state

You need to keep things between runs:

  • What loaded, and when
  • How far each object processed
  • What changed since the previous run
  • What failed, and what was blocked as a result
  • Which tables are still current
  • What should happen on the next run

None of these fit inside one invocation. Whether a table that loaded on Tuesday is now behind a source that loaded on Wednesday is a question about two runs and the graph joining them, so you need something that outlives both.

Weaver keeps it in the platform: bookmarks, current load and validation outcomes, load statistics and an append-only history. It holds current state and history apart, because rebuilding an object ends its current state while its history stays where it is.

Data quality requires handling as well as detection

A post-load test will tell you the customer key is not unique. You still have to decide what happens to those rows.

By the time the test runs they are already in the table, and the models downstream have read them or are about to, so the decision falls to whoever reads the failure message tomorrow.

Weaver classifies every incoming row as an insert, update or delete before writing, and refuses rows it cannot take: a blank primary key, a null in a column declared not null, a duplicate primary key or a duplicate unique key. Each refused row is recorded with one reason, and --fault-tolerant controls whether the valid rows continue or the load stops.

Then there is the case where no single row is wrong and the change is still alarming: the source comes in short, and the load is about to delete most of a table. Weaver measures the change before writing and stops if it goes past what you declared as normal.

Partial failure

Something will be down, a source will be late, a capacity will throttle. What matters is what the estate looks like afterwards, so a run has to record:

  • Which objects succeeded
  • Which failed, and for what reason
  • Which were blocked because a dependency did not load
  • Where incremental state was allowed to advance
  • Where it must not advance, so the next run reads the window again

Weaver records which objects succeeded, failed or were blocked, and only advances a bookmark where the object completed cleanly. A run that succeeded while rejecting rows leaves its bookmark alone, because it has not read the whole window.

Metadata is operational

You usually think of descriptions, columns, keys, foreign keys and lineage as documentation, something you generate for people to read. Weaver also uses them to decide what a load does.

A primary key is what makes a keyed load possible at all: without it Weaver cannot tell you what an update is, what a duplicate is, or what a delete means. Your comparison columns tell it what counts as a change, your thresholds tell it when a change is too big, and your lineage tells it what order to run in and whether a table is behind its sources.

So Weaver keeps the description and the operational state in the same place. They are two facts about the same object, and splitting them leaves you with two things to keep aligned.

Python programs

A lot of real data engineering is not a query. You call an API with pagination and a rate limit, collect files off an SFTP server, unpack an archive somebody still emails weekly, parse a spreadsheet with the header row in the wrong place, or work out a bespoke incremental rule because the source has no reliable timestamp.

None of that is a model function returning a relation. It is a program that runs, does some work, and leaves an output the next stage depends on.

In Weaver that is a Folder: a Python class with a read() method that gets a staging directory and fills it however it likes. Weaver puts its output in the graph, and the Delta table downstream depends on it like anything else.

That crosses two engines, two languages, two Fabric items and a storage boundary, and it is still one pipeline. Something has to run it in order, with a shared record of what has finished.

If your framework's graph stops at the edge of one engine, that coordination does not go away. It moves into an orchestrator, a scheduled trigger, or somebody on the team who knows to run the second thing after the first.

Choosing between them

It comes down to which problem you have. If your data is already landed and modelled and the work is the SQL on top, use dbt: it runs on nearly every warehouse and has years of tooling behind it. If the work is the whole path from a source system to a published table, across Lakehouses and Warehouses, and the hard parts are incremental loading, change handling and knowing what state the estate is in, that is what Weaver is for.

dbt starts with the transformation model. Weaver starts with the operational data estate.
