Weaver vs dbt

dbt is primarily a transformation framework, and a very good one. Weaver is designed around the wider operational lifecycle of data engineering on Microsoft Fabric, including physical structure, loading, operational state and cross-item dependencies.

Four main differences

Fabric-native

dbt supports Fabric through adapters. Weaver models Lakehouses, Warehouses, OneLake, shortcuts, Fabric Environments, Spark and T-SQL directly within one Fabric-specific project model.

A dbt project runs against a single adapter and connection, so a Lakehouse and a Warehouse are separate targets and one graph does not span them. In Weaver they are items in the same graph.

Natural development

dbt dependencies are declared through ref() and source(), while Weaver infers ordinary dependencies from Python imports and SQL references.

This means Python and T-SQL are written as they normally would be, and the dependency graph follows from the code rather than from a parallel set of declarations.

Build and load are separate

In dbt, materialising a model and populating it happen together. Weaver deploys physical structure and processes data as two lifecycles with two commands.

This allows the structure of an entire platform to be installed into a fresh workspace before any data is loaded, and schema changes to be deployed without moving rows.

Operational state is first class

Weaver persists the installed and operational state of each object inside Fabric itself, including load position, current validation state and load statistics.

dbt produces run artifacts such as the manifest and run results, and supports state-aware selection by comparing against a previous manifest. Weaver holds that state in the data platform, where later commands read it directly.

Mature data engineering is more than transformation

Transformation is the most visible part of data engineering and the part most worth getting right. A production pipeline also has physical structure, operational state, change handling and failure behaviour, and each of those needs somewhere to live.

Physical structure

A production pipeline has physical structure as well as transformation logic. Lakehouses, Warehouses, schemas, folders, tables, views, shortcuts and Environments all have their own lifecycle, and they change on a rhythm that has little to do with how often data arrives.

When structure and data are deployed together, every structural change becomes a data event: adding a column means a reload, and checking the shape of a fresh workspace means loading it.

Weaver separates the two. Build makes Fabric match the repository, while load moves the data, and in a large estate either can be run without the other.

Operational state

Production pipelines need state that persists across runs, including:

  • What loaded, and when
  • How far each object processed
  • What changed since the previous run
  • What failed, and what was blocked as a result
  • Which tables are still current
  • What should happen on the next run

Each of these outlives a single invocation. Whether a table that loaded on Tuesday is now behind a source that loaded on Wednesday is a fact about two runs and the graph that connects them, so answering it needs state that survives both.

Weaver keeps that state in the platform as bookmarks, current load and validation outcomes, load statistics and an append-only history. Current state and history are held separately, because a rebuild ends the current state of an object while its history remains.

Data quality requires handling as well as detection

A post-load validation can identify a duplicate key or a null violation. A production load also needs a policy for what happens to the offending rows.

When the check runs after the load, the rows are already in the table and downstream models may already have read them, so the decision falls to whoever reads the failure message.

Weaver classifies every incoming row as an insert, update or delete before writing, and refuses rows it cannot take: a blank primary key, a null in a column declared not null, a duplicate primary key or a duplicate unique key. Each refused row is recorded with one reason, and --fault-tolerant controls whether the valid rows continue or the load stops.

A separate case is a change where no individual row is wrong but the overall movement is unexpectedly large, such as a short extract that would delete most of a table. Weaver measures the change before writing and stops if it exceeds the thresholds the table declares.

Partial failure

Partial failure is a normal operating condition in large pipelines, so what matters is the state of the estate afterwards. A run needs to record:

  • Which objects succeeded
  • Which failed, and for what reason
  • Which were blocked because a dependency did not load
  • Where incremental state was allowed to advance
  • Where it must not advance, so the next run reads the window again

Weaver records which objects succeeded, failed or were blocked, and only advances incremental state where processing completed cleanly. A run that succeeded while rejecting rows leaves the bookmark unchanged, because it has not read its full window.

Metadata is operational

Descriptions, columns, keys, foreign keys and lineage are usually treated as documentation. Metadata becomes operational when the pipeline uses it to make decisions.

A primary key is what makes a keyed load possible, because it determines what counts as an update, a duplicate or a delete. Comparison columns define what counts as a change, thresholds set when a change is too large, and lineage determines execution order and whether a table is behind its sources.

The Catalogue holds the descriptive and operational metadata together, so there is one record of each object rather than two to keep aligned.

Python programs

Many data-engineering tasks are naturally expressed as Python programs rather than as relational transformations, including API ingestion with pagination and rate limits, collecting files over SFTP, extracting archives, parsing awkward spreadsheets, custom incremental logic where a source has no reliable timestamp, and reconciliation between systems.

These are programs that run, do work and produce an output that later stages depend on, rather than functions that return a relation.

In Weaver a Folder is a Python class with a read() method that receives a staging directory and fills it however it needs to. Its output is a node in the dependency graph, so the Delta table downstream depends on it in the ordinary way.

When the framework's graph stops at the boundary of one engine, that coordination moves elsewhere, into an orchestrator, a scheduled trigger or a convention maintained by the team.

Choosing between them

The choice follows from which problem you have. If your data is already landed and modelled and the work is the SQL on top, dbt is mature, portable and very good at that. If the work is the whole path from a source system to a published table across Lakehouses and Warehouses, and the difficulty is in incremental loading, change handling and operational state, that is what Weaver is built for.

dbt starts with the transformation model. Weaver starts with the operational data estate.
