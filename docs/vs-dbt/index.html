Weaver vs dbt

Two different starting questions

dbt is an excellent transformation framework. Weaver starts from a broader question: what does it take to engineer and operate mature data pipelines on Microsoft Fabric?

Four differences that matter

Everything else on this page follows from these.

Fabric-native

Weaver models Fabric concepts directly: several Lakehouses and several Warehouses in one project, OneLake, shortcuts, Fabric Environments, Spark and T-SQL, and one graph across all of them.

A dbt project runs against one adapter and one connection. Fabric adapters exist and work well, but a Lakehouse and a Warehouse are two different targets, and the graph does not span them.

Natural development

Write Python as Python. Write T-SQL as T-SQL. Weaver reads your imports and the relations your SQL selects from, and builds the graph out of what is already in the code.

dbt builds its graph from ref() and source(), which means ordinary references go through Jinja. That is a real design choice with real benefits, and it is also a second way of saying the same thing.

Build and load are separate

Weaver treats deploying physical structure and processing data as two lifecycles with two commands. You can deploy an entire platform's shape into a fresh workspace and load nothing.

In dbt, materialising a model and populating it are the same act. There is no separate structural deployment.

Operational state is first class

The estate has memory. Weaver's Catalogue lives in a Fabric Warehouse and holds what is installed, how far each object has loaded, whether its checks passed, and what has happened.

dbt's artifacts describe a project and its most recent invocation. They are files, produced by a run, rather than state the platform itself keeps.

The longer argument

Mature data engineering is more than transformation

Transformation is the part of data engineering that is easiest to see, and it is the part most worth getting right. But a production pipeline is made of several things, and only one of them is a query.

A pipeline has physical structure

Before any data moves, something has to exist: Lakehouses and Warehouses, schemas, folders, tables, views, shortcuts, and the Environment your Spark code needs its libraries from. That structure has a lifecycle of its own. It gets created, altered, and occasionally dropped and rebuilt, on a rhythm that has nothing to do with how often data arrives.

Treating structure and data as the same act means every structural change is also a data event. Add a column and you reload. Deploy to a fresh workspace and you must load to see whether the shape is right.

This is why Weaver has two commands. Build makes Fabric match the repository. Load moves the data. You can do a lot of one without doing any of the other, and in a large estate you frequently want to.

A pipeline has state

Ask a running data platform some ordinary questions and see where the answers live:

  • What loaded, and when?
  • How far did it get?
  • What changed since last time?
  • What failed?
  • Which of these tables is still trustworthy?
  • What should happen next?

Every one of those is a question about state that outlives a single invocation. A framework whose memory is a file produced by the last run can tell you what that run did. It cannot easily tell you that a table which loaded successfully on Tuesday is now behind a source that loaded on Wednesday, because that is a fact about the relationship between two runs and the graph that joins them.

Weaver keeps that state in the platform: bookmarks, current load and validation outcomes, load statistics, and an append-only history. Current state and history are separate on purpose, because a rebuild ends the current state of an object and leaves its history alone. A rebuild does not unhappen what happened.

Data changes need handling, not only detection

This is the argument we would most like to land, because it is where the gap is widest.

Finding a bad row is one problem. Deciding what the pipeline should do with it is another.

Post-load assertions are excellent at the first. You load the table, then you test it, and the test tells you the customer key is not unique. Good. Now what? The rows are already in the table. The downstream models have already read them, or are about to. The decision about what to do has been deferred to a human reading a failure message.

Operational load semantics ask the question earlier and answer it in the declaration. Weaver classifies every incoming row before it writes anything: insert, update or delete. Rows that cannot be taken are refused with a reason, and set aside where you can look at them. Blank primary key. Null in a column declared not null. Duplicate primary key. Duplicate unique key. One reason per refused row, because a row that is wrong twice over is still one row the load will not take.

Then there is the case where nothing is wrong with any individual row and the change is still alarming. The source came in short and the load is about to delete most of a table. Weaver reads the size of the change before a row moves and stops if it exceeds what the table declared as normal.

The distinction is not about which tool catches more problems. It is about whether the pipeline can act on what it found, or can only report it.

Failure is normal

Something will be down. A source will be late. A capacity will throttle. The question is never whether a run fails, it is what the estate looks like at nine the next morning.

The things that have to be answerable:

  • What succeeded?
  • What failed, and for what reason?
  • What did not run at all, because something it needed did not?
  • Which state was allowed to advance?
  • Which state must not advance, so the next run reads the window again?
  • What should happen on the next run, without anyone reconstructing it by hand?

The principle Weaver follows is that state advances only where it was earned. A bookmark moves for a clean success and nothing else, so a run that succeeded while rejecting rows leaves the bookmark alone: it has not really read its window. Getting this backwards is the failure mode that nobody notices for a month, and then notices very suddenly.

Metadata is operational

Descriptions, columns, keys, foreign keys and lineage are usually treated as documentation: something you generate for people to read. They are also the inputs to decisions the pipeline makes.

A primary key is not a note about the table. It is what makes a keyed load possible: it decides what an update is, what a duplicate is, and what a delete means. Comparison columns decide what counts as a change. Thresholds decide when a change is too large. Lineage decides execution order and answers whether a table is behind its sources.

A mature data platform should know itself.

Which is what the Catalogue is for. It holds the description and the operational state in the same place, because they are the same kind of fact about the same object, and a platform that separates them ends up with two things to keep aligned.

Sometimes data engineering is a program

A great deal of real data engineering is not a query. It is a program.

You have to call an API with pagination and a rate limit. Collect files off an SFTP server. Unpack an archive somebody still emails weekly. Parse a spreadsheet with a header row in the wrong place. Reach for a third-party library because the format is not one you are going to write a parser for. Work out a bespoke incremental rule because the source has no reliable timestamp. Reconcile two systems that disagree in an interesting way.

None of that is a model function returning a relation. It is a program that runs, does some work, and produces an output that later stages depend on.

Sometimes the right abstraction for data engineering is a program, not a model.

In Weaver a Folder is that. It is a Python class with a read() method that gets a staging directory and fills it however it likes. Its output is a first-class node in the graph, and the Delta table downstream of it depends on it the same way it would depend on anything else.

If the framework's graph stops at the boundary of one engine, the coordination does not disappear. It just moves somewhere else: an orchestrator, a scheduled trigger, a naming convention, a person who knows to run the second thing after the first.

Where that leaves us

dbt starts with the transformation model.

Weaver starts with the operational data estate.

The choice follows from which problem you have. If your data is already landed and modelled and the work is the SQL on top, dbt is mature, portable and very good at that. If the work is the whole path from a source system to a published table, across Lakehouses and Warehouses, and the hard parts are incremental loading, change handling and knowing what state the estate is in, that is what Weaver is for.
