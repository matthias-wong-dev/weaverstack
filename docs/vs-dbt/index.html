Weaver vs dbt

dbt is a transformation framework. Weaver covers the wider operational lifecycle of data engineering on Microsoft Fabric: physical structure, loading, operational state and dependencies that cross Fabric items.

How Weaver differs from dbt

Fabric-native

dbt reaches Fabric through adapters. Weaver models Lakehouses, Warehouses, OneLake, shortcuts, Fabric Environments, Spark and T-SQL directly.

dbt uses one adapter and one connection per project, so a Lakehouse and a Warehouse are separate targets and no single graph spans them. Weaver represents them as two items in the same graph.

Natural development

In dbt you declare dependencies with ref() and source(). Weaver reads them out of your Python imports and your SQL references.

Python remains Python and T-SQL remains T-SQL. Weaver derives the graph from the code rather than from a separate set of dependency declarations.

Build and load are separate

In dbt, materialising a model and populating it are the same act. Weaver splits them into two commands.

Build can install a platform's structure into a fresh workspace before loading data, and deploy schema changes without moving rows.

Operational state is first class

Weaver keeps each object's installed and operational state inside Fabric: how far it loaded, whether its checks passed, and what the last load changed.

dbt writes run artifacts such as the manifest and run results, and selects on state by comparing against a previous manifest. Weaver keeps that state in the data platform, where subsequent Weaver commands use it directly.

Operational data engineering

Transformation is the most visible part of data engineering, and the part most worth getting right. A production pipeline also has physical structure to deploy, state to carry between runs, bad rows to deal with and failures to survive.

Physical structure

Lakehouses, Warehouses, schemas, folders, tables, views, shortcuts and Fabric Environments have a lifecycle independent of data loading. They are created, altered and rebuilt on a different rhythm from data arrival.

Deploying structure and data together makes every structural change a data event. A column addition can require a reload, and a fresh workspace cannot be checked until it has loaded.

Build makes Fabric match the repository and load moves data. The two commands can run independently.

Operational state

Operational state persists between runs:

  • What loaded, and when
  • How far each object processed
  • What changed since the previous run
  • What failed, and what was blocked as a result
  • Which tables are still current
  • What should happen on the next run

Current state depends on outcomes from multiple runs and the dependency graph connecting them. A table can become stale when an upstream source loads again.

Weaver keeps it in the platform: bookmarks, current load and validation outcomes, load statistics and an append-only history. It holds current state and history apart, because rebuilding an object ends its current state while its history stays where it is.

Data quality requires handling as well as detection

Post-load validation and row-handling policy are different concerns. A uniqueness failure detected after loading does not determine how the invalid rows are handled.

Post-load tests run after rows have entered the target table, so row-handling policy must apply during the load.

Weaver classifies every incoming row as an insert, update or delete before writing, and refuses rows it cannot take: a blank primary key, a null in a column declared not null, a duplicate primary key or a duplicate unique key. Each refused row is recorded with one reason, and --fault-tolerant controls whether the valid rows continue or the load stops.

A load can be structurally valid while representing an implausibly large change. Weaver measures the change before writing and stops it when it exceeds the declared threshold.

Partial failure

Source availability and capacity can cause partial failures. Weaver records:

  • Which objects succeeded
  • Which failed, and for what reason
  • Which were blocked because a dependency did not load
  • Where incremental state was allowed to advance
  • Where it must not advance, so the next run reads the window again

Weaver records which objects succeeded, failed or were blocked, and only advances a bookmark where the object completed cleanly. A run that succeeded while rejecting rows leaves its bookmark alone, because it has not read the whole window.

Metadata is operational

Weaver uses descriptions, columns, keys, foreign keys and lineage for execution as well as documentation.

A primary key enables a keyed load. Without it, Weaver cannot identify updates, duplicates or deletes. Comparison columns define changes, thresholds constrain change size, and lineage determines run order and staleness.

The Catalogue holds metadata and operational state for the same object.

Python programs

Weaver supports Python programs for API acquisition, SFTP collection, archive extraction, spreadsheet parsing and source-specific incremental rules.

These programs produce outputs for downstream stages rather than returning relations from model functions.

In Weaver, this is a Folder: a Python class with a read() method. Weaver provides a staging directory, and the method writes its output there. Weaver adds that output to the graph, and downstream Delta tables depend on it like any other object.

This pipeline crosses two engines, two languages, two Fabric items and a storage boundary. Its execution requires one dependency graph and shared operational state.

A graph limited to one engine leaves cross-engine coordination to an orchestrator or scheduled trigger.

Overlap and emphasis

dbt and Weaver overlap substantially. dbt is centred on transformation and modelling across data platforms. Weaver covers a broader part of a Fabric pipeline, including loading, cross-item dependencies and persistent operational state.

dbt starts with the transformation model. Weaver starts with the operational data estate.
