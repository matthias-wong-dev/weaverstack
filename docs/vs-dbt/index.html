dbt models transformations. Weaver operates the Fabric estate.

dbt centres the transformation model. Weaver centres the operable Fabric estate: its Lakehouses, Warehouses, physical structure, loading, dependencies and state between runs.

The practical differences

One graph across Fabric engines

A Weaver project can place Python and Delta work in a Lakehouse, T-SQL in a Warehouse, and the shortcut between them in the same dependency graph.

dbt uses separate Fabric adapters for Warehouse and Spark work. A project runs through one adapter target, so the boundary between those engines remains outside that project's graph.

Dependencies stay in the code

Weaver reads Python imports and ordinary SQL relation references. The code itself establishes the order.

dbt uses ref() and source(). That is a coherent model, but it means SQL references are written in dbt's templating vocabulary.

Build is not load

weaver build deploys schemas, tables, views, shortcuts and runnable load code without moving data. weaver load runs the installed data work later.

A dbt model is materialised and populated by the same run. Weaver lets you deploy the structure and run its data load separately.

Operational state stays with the estate

Weaver records installed objects, bookmarks, load and validation outcomes and row-change counts in the Weaver Catalogue.

dbt Core writes artefacts such as manifest.json and run_results.json. Weaver's next command reads its state from Fabric rather than requiring a previous artefact to be supplied.

Mirror branches an estate

Weaver can fork an installed Catalogue and let development targets borrow unchanged Warehouse and Lakehouse data through views and OneLake shortcuts.

dbt-fabric documents table cloning within a Warehouse. Mirror operates across the installed multi-item estate and lets each item be borrowed or materialised separately.

Warehouse identity is declared with the table

In Weaver, Identity: Customer key adds a Fabric-managed bigint IDENTITY column and keeps it out of load inserts. The model author does not write surrogate-key allocation logic.

The current dbt-fabric model configuration reference documents no equivalent identity-column setting. Existing identity properties can be preserved during some adapter operations, but they are not declared as part of a dbt model contract.

The identity declaration

One line removes the need to generate surrogate keys in model SQL.

Warehouse/Curated/Sales.Customer.sql
/*
Table ID: Sales.Customer
Primary key: Customer id
Identity: Customer key

Schema:
  Customer id: varchar(50)
  Customer name: varchar(200)
*/

Fabric generates the identity value when Weaver inserts a new row. Weaver supports this for Warehouse tables today. Delta identity is planned, but Microsoft currently lists identity-column writing as unsupported across Fabric's Delta Lake experiences.

Choose by the boundary you need

For transformation modelling inside one supported engine, dbt has a large ecosystem and a familiar workflow. Weaver is for the point where the unit of engineering is the Fabric estate itself: Python acquisition, Lakehouse and Warehouse objects, cross-item dependencies, deployment and recovery.
