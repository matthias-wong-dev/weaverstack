Keep your Python. Get the engineering around it.

A little project structure puts familiar Python and Spark SQL into a managed Lakehouse project.

Start where the data starts

A couple of spreadsheets, an API feed or a growing set of Delta tables should not need a second project just to organise the first. Put each file or table definition under its Lakehouse, add its metadata, and keep writing ordinary Python.

Folders participate alongside tables. A Python table can import its upstream Folder; Weaver uses that import to put the file work first. You still write the extraction and transformation.

Inside a Python Table: read the upstream Folder 
from Files.Parcel__Events import Parcel__Events
from weaver import Table

class Parcel__Event(Table):
    def read(self):
        source = Parcel__Events(self).spark_path()
        return self.spark.read.option("header", True).csv(source)

This is the Python body, not a complete project: the Table and Folder also need their metadata. The tutorial supplies both complete files.

Develop without making a second full copy

Mirror lets a development estate borrow unchanged Lakehouse data through OneLake shortcuts. Build the selected work that needs to diverge and materialise it locally, leaving other data at its source.

Borrowed data remains live at the source. Mirror is not a point-in-time backup.

Incremental work with a memory

Each consumer keeps its own successful-processing bookmark. Weaver stages incoming data, applies supported upserts and explicit deletions, and records row changes and progress. File-change helpers support incremental file work.

You decide how to identify source changes and deletions. A missing row in staging is not automatically a deletion, and Weaver does not invent change-data capture for an arbitrary source.

A failure need not stop unrelated work

Choose fault-tolerant loading to continue independent branches when another fails. Recorded failed, blocked and stale state makes the next run inspectable. There is no promise of a universal automatic retry or whole-run rollback.

Fabric details do not become another pipeline

Weaver coordinates supported cross-item dependencies and SQL endpoint-readiness waits, and schedules independent work concurrently. Work from a local project or a Fabric notebook without a separate always-on Weaver service.

Python Load work still needs Weaver available in its Fabric runtime. Spark SQL Tables and Views use explicit dependency declarations; do not assume every SQL reference is inferred.
