Start with what you know

Python and Spark SQL, together

Use Python and Spark SQL together for Lakehouse Files and Delta Tables in the same dependency model.

Ordinary T-SQL

Keep ordinary SELECTs, without a proprietary modelling language or macros.

Native Power BI

Keep PBIP, TMDL and native Report definitions rather than converting to a Weaver-only format.

Desktop, Fabric Notebooks, or both

Build and operate the same project from desktop Python or the CLI, an attached Fabric Notebook, or both.

Install with pip

Install the open-source Python package with pip, without another Weaver server, orchestration service or software licence.

Existing Fabric services, compute and workspace permissions still apply. Lakehouse processing uses Fabric’s Spark runtime, not a separate Weaver orchestration service.

Pipelines, dependencies and data quality

One dependency graph across Fabric

Order selected managed Lakehouse work, Warehouse T-SQL and dependent Semantic Model refreshes in one DAG.

Generated Warehouse pipelines

A SELECT becomes a Table with generated staging, declared-key matching, row-change reconciliation and recorded results.

Managed Lakehouse pipelines

Materialise Files, Python and Spark SQL into managed Delta Tables without hand-building another orchestration project.

Dependency discovery

Python imports and supported T-SQL references supply dependencies; Spark SQL uses explicit declarations.

Incremental inserts, updates and deletes

Apply insert/update candidates and explicit delete keys under the declared policy, without rebuilding every target.

Per-consumer bookmarks

Each loadable Table or Folder keeps its own clean processing boundary, even when consumers share a source.

Tests and Assumptions

Compare expected and actual results or catch rule-breaking rows through supported Python, SQL and DAX validations.

Data-quality safeguards

Record rejected input and refuse proposed update/delete changes that exceed active stability thresholds.

Power BI, engineered for organisations

Native Semantic Model deployment

Deploy the PBIP/TMDL model you already author while preserving its native source files.

Organisation-wide modelling standards

Apply shared native TMDL policy across Semantic Models instead of repeating formats and conventions.

Built-in modelling annotations

Hide foreign keys, generate measure selectors and apply supported model rules through native TMDL annotations.

Custom Python annotations

Implement project-specific modelling conventions in trusted Python when native policy and built-ins are not enough.

Semantic Model composition

Reuse a native model foundation to produce audience variants without maintaining complete copies.

DAX validation and SQL reconciliation

Check DAX measures against independent expectations, including SQL calculations over managed Lakehouse or Warehouse sources.

Verified Report deployment

Deploy the same authored Report to different destinations, resolving and verifying its intended model and workspace binding.

Supported native model/Report deployment also works in an appropriately licensed Power BI service workspace, without Lakehouse/Warehouse work or a Weaver Catalogue.

Run and inspect an estate · Operation boundaries

Visibility, included

Weaver comes with a Power BI dashboard over the catalogue. One command deploys it beside your estate.

One command

weaver catalogue-dashboard deploys the semantic model and Report beside the catalogue, and brings them up to date on the next run.

Live over Direct Lake

The model reads the catalogue’s tables over Direct Lake, so each page shows your Weaver-managed estate as work settles.

Free to tweak

It is an ordinary Power BI Report. Tweak it to fit your needs, or throw it away and build your own over the catalogue.

When your estate gets complicated

One project, multiple environments

Keep source files and logical identities while workspace configuration selects physical item and model destinations.

Mirror: develop without copying everything

Borrow installed Lakehouse/Warehouse data through Shortcuts and Views, then materialise selected changed or affected work locally.

Incremental Build

Reconcile changed source-data definitions and affected selected descendants, retaining certified unchanged source work.

Build previews

Inspect selected actions, physical targets and destructive effects through a read-only Build plan.

Controlled deployment bundles

Review and hand off frozen, destination-specific installation plans without replanning during Install.

Cross-engine publication and readiness

Order supported OneLake publication and SQL endpoint-readiness barriers before dependent cross-engine consumers.

Protect important data

Keep irreplaceable sources outside managed targets and use Build replacement guards for protected owned objects.

Bundles are destination-specific. Build replacement guards do not protect data from Load, Wipe or deliberate resets.

From three objects to three thousand.

The scale benchmark records first-load and incremental processing separately. In the synthetic F64 benchmark, the 3,000-object estate’s first Load took about an hour; later measured incrementals were around 13 minutes. The first incremental day took about 19 minutes.
