How it works

What actually happens when you use Weaver

There are two halves to it. Build turns your repository into an installed Fabric estate. The Catalogue is Weaver's understanding of that estate, and load, test and health all work from it. Get those two ideas and the rest follows.

The whole shape, in one picture

1. The repository

Your repository is the logical description of the data platform: what exists, and what it is made of. It says nothing about which Fabric workspace it lands in.

Objects sit under the Fabric item that owns them. A Lakehouse item holds Python folders, Delta tables and Spark SQL. A Warehouse item holds T-SQL tables and views. Either can hold Tests and Assumptions. Alongside them are shortcut declarations, schema and folder documents, and the metadata each object carries in its header: description, lineage, primary key, column types, thresholds.

One separate file, workspace-config.yml, says where it all goes. That is the only file you change to point the same repository at a development workspace instead of a production one.

A Weaver item is logical. A target is physical. Lakehouse/Landing is the item you author against. The Fabric Lakehouse it is built into might be called Landing_Dev. Build reads that binding from workspace configuration; load, test and health read it from the Catalogue. So one sequence of commands runs against both, and only the configuration file changes.

2. Build

Build makes Fabric match your repository.

This is the moment your work first enters the installed estate. Build reads the repository, reads what is already there, works out the difference, and installs it. It handles:

  • Schemas and folders
  • Delta tables in a Lakehouse
  • Tables and views in a Warehouse
  • Shortcuts between items
  • The runnable load code for each object, as a Python module or a T-SQL procedure
  • The metadata registration that makes all of it known

Build changes structure. It does not load the data.

That separation is one of the most important choices in Weaver, and it is worth being clear about. You can deploy the shape of an entire platform into a fresh workspace, look at it, and load nothing. You can change a column type and rebuild without moving a row. Structural deployment and data processing are two different lifecycles with two different risks, and Weaver keeps them apart.

A build is incremental. It compares the repository against what is installed and does the work that is actually different. It reads the real state to decide: the Catalogue over TDS, a Lakehouse's views over Spark SQL, a Lakehouse's objects from storage, a Warehouse over TDS. Nothing is planned against a guess.

Certification is per object. Before a rebuild, the objects you selected and everything downstream of them stop being certified, and each one becomes certified again only once it has built.

3. The Catalogue

The repository describes the estate. The Catalogue is Weaver's installed understanding of it.

This is the centre of Weaver, and it is more than documentation. It is the thing every operation after build reads to decide what to do.

Three different things, and it helps to keep them apart:

The repository

What you want the estate to be. Files in source control. Changes when you write code.

Fabric

The physical platform. Real Delta files, real Warehouse tables, real shortcuts. Changes when a build or a load runs.

The Catalogue

What Weaver knows about the installed estate and how it is running. Changes when either of the other two does.

The Catalogue lives in the _ schema of a Fabric Warehouse you name, as sixteen ordinary tables. That Warehouse can be one of its own or one you already use for your own schemas. Weaver owns _ in it and nothing else.

What it holds

What is installed

  • Every installed object, its role and its type
  • What depends on what
  • Shortcuts between items
  • Which physical Fabric item each logical item is bound to
  • Descriptions, columns, keys and foreign keys

How it is running

  • How far each object has loaded, as a bookmark
  • The current load outcome for each object
  • The current validation outcome for each object
  • Row counts for every insert, update and delete a load made
  • An append-only history of what has happened

Current state and history are different on purpose. A current-state row describes one object's current physical incarnation: drop and rebuild the object and that row ends with it, because the new table has loaded nothing yet. History is appended and a rebuild leaves it alone, because a rebuild does not unhappen what happened.

Because the Catalogue is a Warehouse, reading it costs a TDS query. A Warehouse-only project therefore starts no Spark session at all.

4. Load

Load runs the data work, from the graph that is installed.

Load does not read your repository. It reads the Catalogue, derives the dependency graph from the rows already there, and runs each loadable object in order. From the Catalogue it knows:

  • Which objects are loadable, and which are views that materialise nothing
  • What depends on what, across Fabric items as well as inside them
  • How far each object has already processed
  • What happened to each one last time

Naming an item loads everything it owns, in dependency order. Naming none loads every item the Catalogue records an installation for. An item is a hard boundary: a dependency never pulls in an item you did not name.

Underneath that there is quite a lot going on. Incremental loading, row-level change handling, rejected rows and recovery after a failure are all part of it. They are covered in the advanced section below.

5. Test

Your checks are part of the installed estate, not a separate thing that runs beside it.

A Test or an Assumption is authored under the item it belongs to, discovered like any other object, compiled by a build, and installed alongside the tables it reads. It ends up in the same graph, and its result is recorded in the Catalogue rather than only printed.

Weaver has two kinds and keeps them distinct:

Test

Compares an expected relation with an actual one, and passes when the symmetric difference is empty. It tells you both what is missing and what turned up that should not have.

Assumption

States a condition you are relying on and returns the rows that contradict it. Holding looks like an empty result. There is no second side to correlate, so an Assumption declares no primary key.

Both compile to something you can run on your own. A T-SQL validation becomes a stored procedure anyone can execute without Weaver in the room.

Neither one materialises a data object. A Test carries an ordinary Schema.Object identity so it can be named and recorded, and it is held apart from the documents an item materialises, so having an identity never routes it into table or view DDL. That is also why weaver load does not run your tests: an artefact is known by its declared role, never inferred from being a file or a procedure.

6. Health

Health asks whether the estate is currently healthy.

This is a different question from "did the last command work", and it is usually the more useful one.

Health reads the Catalogue and interprets the current state across the whole installed estate. It can tell you that an object loaded successfully and is still a problem, because something it reads has moved on since. That is a question about the graph, not about any one run, which is why it needs the installed dependencies to answer it.

It reports things like:

  • Objects whose last load failed, or was blocked by something upstream
  • Objects that are behind their sources, where an ancestor has loaded more recently than they have
  • Objects with no settled load recently enough to count as current
  • Validations that are currently failing
  • Certified objects that are not physically there

By default anything that has not settled a load in the last 24 hours reads as stale, and --as-of moves that line.

Going deeper

The mechanics underneath

You now have the lifecycle. This part is how Weaver handles the harder pipeline problems. Read it when you need it.

Dependency discovery

This is the foundation of the whole graph, so it comes first.

Python: the dependency is the import

You write ordinary Python. Weaver reads what you imported and used.

Lakehouse/Landing/Tables/Sales__Customer.py
# The dependency is this line. Nothing else declares it.
from Files.Sales__Customers import Sales__Customers

from weaver import Table


class Sales__Customer(Table):
    def read(self):
        exported = Sales__Customers(self).spark_path()
        return self.spark.read.option("header", True).csv(exported)

Python dependencies come from the code you import and use.

T-SQL: the dependency is the relation you select from

You write ordinary T-SQL. No Jinja, no macros, no ref().

Warehouse/Curated/Sales.CustomerByRegion.sql
select c.[Customer id]
     , c.[Customer name]
     , r.[Region name]
  from [Sales].[Customer] c
  join [Sales].[Region] r on r.[Region code] = c.[Region code];

T-SQL dependencies come from the relations the SQL actually references.

Discovery is static. Weaver never imports your object modules to find out what they depend on, so working out the graph runs no code of yours and needs no Fabric session.

You write normal Python and normal SQL. Weaver works out what depends on what.

Shortcuts

A Warehouse cannot read Delta files. It reads a Lakehouse's SQL endpoint. That is a real Fabric constraint, and in most setups it becomes a platform configuration task that lives somewhere other than your pipeline.

In Weaver a shortcut is a declaration in your repository, and it takes its place in the graph like anything else:

Warehouse/Curated/shortcuts.yml
logical:
  Warehouse/Curated/Sales.Customer: Lakehouse/Landing/Tables/Sales.Customer

The Warehouse object now selects from [Sales].[Customer] as if it were local. Neither item has to know where the other one is physically built, because both sides are logical names that the Catalogue resolves. Build creates the shortcut; load waits for the Lakehouse table before running the Warehouse object that reads through it.

Incremental load and bookmarks

An object can know how far it has already processed. Weaver keeps that as a bookmark: one row per loadable table or folder, holding the UTC instant immediately before its most recent clean load began.

The rule that governs it is simple and worth stating plainly, because it is the safe direction:

A bookmark advances on a clean success and nothing else. A load that succeeded but rejected rows leaves it alone, because it has not really read its window. A load that failed leaves it alone. An object that was dropped and rebuilt loses its bookmark entirely, so the next load reads everything.

Too old means replay. Too far advanced means silently missing data. Weaver prefers replay.

In a Lakehouse, your Python reads the bookmark directly and decides what to do with it:

an incremental folder read
def read(self):
    # Files changed after the last clean load, and when.
    return Source__Export(self).files_since(self.bookmark())

There is a matching deleted_since(bookmark) for files that were retired. An object with no bookmark row reads as a sentinel far in the past, so an incremental read asks for everything and the first run is a full one without any special case.

Warehouse tables are different, and it is worth being precise. Weaver maintains the bookmark for every loadable Warehouse table and uses it to decide whether a Static table has already been loaded once. Authored T-SQL does not read a bookmark window of its own. Incremental behaviour for a Warehouse table is about what absence means, which is the next paragraph.

Incremental: true changes what it means for a key to be missing from the source. A non-incremental keyed table treats the source as the whole truth, so a key that is absent retires the target row. An incremental table treats the source as a window, so a key it does not carry says nothing at all about the target's row. Incremental requires a primary key, because without one there is nothing to reconcile against.

Changing data, not just detecting it

When a keyed table loads, Weaver classifies every incoming row as an insert, an update or a delete before it writes anything. That classification is a real relation the load can look at, which is what lets it make decisions before a row moves.

Two kinds of problem, handled differently:

A bad incoming row

Recoverable. It is refused with a reason and set aside: a blank primary key, a null in a column declared not null, a duplicate primary key, or a duplicate unique key. Whether the surviving rows load or the whole load stops is what --fault-tolerant decides.

A change that would leave the target invalid

Not recoverable. There is no single row to blame, so the load stops before it writes anything. Fault tolerance does not override this: that setting governs incoming rows, and this is the target's own validity.

There is also a stability gate, for the case where nothing is technically wrong but far too much is about to move. A table can declare how much change it considers normal, and by default a load stops if it would delete more than 5% or update more than 20% of the target. The gate does not apply to small tables at all: below a million rows it is not consulted, so at the defaults a load is removing more than 50,000 rows or changing more than 200,000 before the question is even asked.

Every gate is reached before anything is written. Refusing is a decision not to start, rather than something to unwind.

Failure, and what happens next

Things fail. What matters is what the estate looks like afterwards.

  • What failed is recorded. The outcome goes into the Catalogue, so the next command and the next person both know.
  • Downstream work does not carry on regardless. An object whose source did not load is blocked, and that is a distinct outcome from having failed on its own account.
  • State only advances where it earned it. A bookmark moves for a clean success and for nothing else, so a partial run cannot quietly convince the next one that a window was read.
  • Recovery does not mean starting again. The next run reads the recorded state and picks up from it. Nothing pretends the whole estate never ran.

By default a load stops at the first failure. --fault-tolerant continues down branches that do not depend on what failed, which is the right choice for a nightly run where you would rather get most of the estate loaded and deal with one broken source in the morning.

And when you come back to it, weaver health is the question to ask. It reads the recorded state and tells you what is currently wrong, rather than making you reconstruct it from logs.
