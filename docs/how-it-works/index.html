How Weaver works

Build installs your repository into Fabric and records what it did in the Catalogue. Load, test and health all work from there.

Build, load, test and health

You build, then load, then test. Health tells you where the estate stands afterwards.

buildmake Fabric match your repository
→
loadrun the data work
→
testrun your checks
→
healthask how the estate is

Build creates the tables, views, shortcuts and load code your repository describes, and records them in the Catalogue. Load and test then work from what it installed, and health reads the same records to tell you whether the estate is current.

1. The repository

Your repository describes the estate logically. A separate file, workspace-config.yml, says which Fabric resources those logical items map to.

You put each object under the Fabric item that owns it. A Lakehouse item holds Python folders, Delta tables and Spark SQL; a Warehouse item holds T-SQL tables and views. Either can hold Tests and Assumptions. Alongside them you declare shortcuts, schema and folder documents, and the metadata each object carries in its header: description, lineage, primary key, column types and thresholds.

Because the workspace configuration sits in its own file, you can point the same repository at development or production without touching a single object.

A Weaver item is logical; a target is physical. You write against Lakehouse/Landing, and Weaver might build it into a Fabric Lakehouse called Landing_Dev. Build takes that binding from your workspace configuration, and load, test and health take it from the Catalogue, so the same commands run against either environment.

2. Build

Build compares your repository with what is in Fabric now, and applies the difference. It creates and maintains:

  • Schemas and folders
  • Delta tables in a Lakehouse
  • Tables and views in a Warehouse
  • Shortcuts between items
  • The runnable load code for each object, as a Python module or a T-SQL procedure
  • The Catalogue records that make all of it known

Build changes structure without loading data, so schema and object changes deploy independently from data movement.

Weaver keeps these apart because they change at different times. You can install the shape of an entire platform into a fresh workspace and load nothing, or change a column type and rebuild without moving a row.

Builds are incremental, and Weaver compares against what is really there rather than a cached model. It reads the Catalogue over TDS, a Lakehouse's views over Spark SQL, a Lakehouse's objects from storage, and a Warehouse over TDS.

Weaver certifies objects one at a time. When you rebuild, it un-certifies what you selected and everything downstream, then certifies each one again as it builds.

3. The Catalogue

The Catalogue is where Weaver records what it installed and how it is running. Load, test and health all read it.

The repository

The estate you want, as files in source control. It changes when you write code.

Fabric

The real thing: actual Delta files, Warehouse tables and shortcuts. It changes when you build or load.

The Catalogue

What Weaver knows about the other two. It changes whenever either of them does.

Weaver keeps it as ordinary tables in the _ schema of a Fabric Warehouse you name. Give it a Warehouse of its own, or use one you already have, because Weaver owns _ and nothing else in there.

What it holds

What is installed

  • Every installed object, its role and its type
  • What depends on what
  • Shortcuts between items
  • Which physical Fabric item each logical item is bound to
  • Descriptions, columns, keys and foreign keys

How it is running

  • How far each object has loaded, as a bookmark
  • The current load outcome for each object
  • The current validation outcome for each object
  • Row counts for every insert, update and delete a load made
  • An append-only history of what has happened

Weaver treats current state and history differently. A current-state row describes the object as it exists now, so if you drop and rebuild it that row ends with it, because the new table has loaded nothing. History is append-only, and a rebuild leaves it alone.

Because the Catalogue lives in a Warehouse, reading it is just a TDS query. A Warehouse-only project therefore never starts a Spark session.

4. Load

Load runs the data work from what build installed, not from your repository.

It reads the Catalogue, rebuilds the dependency graph from the rows already there, and runs each loadable object in order. From those rows it knows:

  • Which objects are loadable, and which are views that materialise nothing
  • What depends on what, across Fabric items as well as inside them
  • How far each object has already processed
  • What happened to each one last time

Name an item and Weaver loads everything it owns, in dependency order. Name none and it loads every installed item. Items are a hard boundary either way: a dependency never drags in an item you did not ask for.

The mechanics underneath cover incremental loading, row-level change handling, rejected rows and recovery after failure.

5. Test

Tests and Assumptions are installed with the objects they validate, participate in the dependency graph, and have their results recorded in the Catalogue.

You write a Test or an Assumption under the item it belongs to. Weaver discovers it like any other object, compiles it during a build and installs it alongside the tables it reads.

Test

A Test compares what you expect with what is actually there, and passes when the two match exactly. It tells you what is missing and what turned up that should not have.

Assumption

An Assumption returns the rows that break a condition you are relying on, so it passes when it returns nothing. There is no second side to line up against, so it declares no primary key.

Both compile to something you can run on your own. A T-SQL validation becomes a stored procedure, and you can execute it without Weaver.

Neither one materialises anything. A Test carries an ordinary Schema.Object identity so Weaver can name it and record it, but Weaver holds it apart from the documents an item materialises, so it never turns into table or view DDL. Weaver goes by an artefact's declared role rather than guessing from its file type, which is why weaver load leaves your validations alone.

6. Health

Health tells you where the estate stands now, not how the last command went.

It reads the Catalogue across the whole installed estate, so it can flag an object that loaded perfectly well and is stale anyway, because something it reads loaded again afterwards. To answer that you need the dependency graph, not just the last run's exit code.

It reports:

  • Objects whose last load failed or was blocked upstream
  • Objects behind their sources, where an ancestor has loaded more recently
  • Objects with no settled load recent enough to count as current
  • Validations that are currently failing
  • Certified objects that are not physically there

By default anything that has not settled a load in the last 24 hours counts as stale. Use --as-of to move that line.

The mechanics underneath

How Weaver handles dependency discovery, shortcuts, incremental state and failure.

Dependency discovery

Python dependencies

Weaver reads your imports and the symbols you use.

Lakehouse/Landing/Tables/Sales__Customer.py
# The dependency is this line. Nothing else declares it.
from Files.Sales__Customers import Sales__Customers

from weaver import Table


class Sales__Customer(Table):
    def read(self):
        exported = Sales__Customers(self).spark_path()
        return self.spark.read.option("header", True).csv(exported)

T-SQL dependencies

Weaver reads the relations your query selects from. No Jinja, no macros, no ref().

Warehouse/Curated/Sales.CustomerByRegion.sql
select c.[Customer id]
     , c.[Customer name]
     , r.[Region name]
  from [Sales].[Customer] c
  join [Sales].[Region] r on r.[Region code] = c.[Region code];

Weaver never imports your object modules to find this out. It reads them statically, so working out the graph runs none of your code and needs no Fabric session.

Shortcuts

A Warehouse cannot read Delta files, so it reaches a Lakehouse through its SQL endpoint. You declare that shortcut in the repository, and Weaver puts it in the dependency graph like anything else.

Warehouse/Curated/shortcuts.yml
logical:
  Warehouse/Curated/Sales.Customer: Lakehouse/Landing/Tables/Sales.Customer

Your Warehouse object then selects from [Sales].[Customer] as though it were local. Both sides are logical names, and Weaver resolves them through the Catalogue, so neither item needs to know where the other is physically built. Build creates the shortcut; load runs the Warehouse object after the Lakehouse table it reads.

Incremental load and bookmarks

Weaver remembers how far each object got as a bookmark: one row per loadable table or folder, holding the UTC instant just before its most recent clean load began.

A bookmark advances only after a clean load. A run that rejects rows leaves it where it was, and so does a run that fails. Drop and rebuild an object and it loses its bookmark entirely, so the next load reads everything.

Leave a bookmark behind and you replay some data. Move it too far and you skip data without noticing, so Weaver only moves it after a clean load.

In a Lakehouse you read the bookmark yourself and decide what to do with it.

an incremental folder read
def read(self):
    # Files changed after the last clean load, and when.
    return Source__Export(self).files_since(self.bookmark())

There is a matching deleted_since(bookmark) for files that have been retired. An object with no bookmark row reads as an instant far in the past, so your first run is a full load and you write no special case for it.

Warehouse tables work differently. Weaver keeps a bookmark for every loadable Warehouse table and uses it to tell whether a Static table has already loaded, but your T-SQL does not read a bookmark window of its own. For a Warehouse table, incremental means something else, which is what a missing key tells you.

Incremental: true changes what a missing key means. Without it, Weaver treats your source as the whole truth, so a key that is absent retires the target row. With it, the source is only a window, and a key it does not carry says nothing at all about the target. You need a primary key either way, because otherwise there is nothing to reconcile against.

Change handling

When a keyed table loads, Weaver works out whether each incoming row is an insert, an update or a delete before it writes anything. That answer is a relation it can query, so the load can look at the whole change before applying any of it.

A bad incoming row

Recoverable. Weaver refuses the row, records why, and sets it aside: a blank primary key, a null in a column you declared not null, a duplicate primary key or a duplicate unique key. Pass --fault-tolerant and the surviving rows load anyway; leave it off and the whole load stops.

A change that would leave the target invalid

Not recoverable. No single row is at fault, so the load stops before writing anything. --fault-tolerant will not get you past this one: it governs incoming rows, and this is about the target itself.

A load can be structurally valid while representing an implausibly large change. You declare the movement a table treats as normal, and Weaver stops a load that would delete more than 5% or update more than 20% of the target by default. It skips this check below one million rows, so the default thresholds apply only above 50,000 deleted rows or 200,000 updated rows.

All of these run before Weaver writes anything, so refusing a load means never starting it, not unwinding it afterwards.

Failure and recovery

Partial failures require durable state for recovery.

  • Outcome. Each object's outcome is recorded in the Catalogue.
  • Blocked dependencies. If an object's source does not load, Weaver marks the object blocked rather than failed.
  • Bookmark position. A bookmark advances only after a clean load, so a partial run cannot skip unprocessed data on the next run.
  • Retry. The next run reads the window the previous run left unprocessed.

By default a load stops at the first failure. --fault-tolerant continues independent branches.

weaver health reads this state and reports the current condition of the estate.
