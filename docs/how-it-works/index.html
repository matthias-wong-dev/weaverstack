How Weaver works

Build installs the repository into Fabric and records the result in the Catalogue. Load, test and health then operate from that installed state.

The four commands

The main lifecycle is build, load and test, while health reports the current state of the installed estate.

buildmake Fabric match your repository
→
loadrun the data work
→
testrun your checks
→
healthask how the estate is

Build creates the tables, views, shortcuts and load code described in the repository and records them in the Catalogue. Load and test then work from that installed state, while health uses it to show whether the estate is current.

1. The repository

The repository describes the logical data estate, while workspace-config.yml maps those logical items to physical Fabric resources.

Objects sit under the Fabric item that owns them. A Lakehouse item holds Python folders, Delta tables and Spark SQL, and a Warehouse item holds T-SQL tables and views. Either can hold Tests and Assumptions. Alongside them are shortcut declarations, schema and folder documents, and the metadata each object carries in its header, including description, lineage, primary key, column types and thresholds.

Because the workspace configuration is a separate file, the same repository can be pointed at a development or a production workspace without changing any object.

A Weaver item is logical and a target is physical. You author against Lakehouse/Landing, which might be built into a Fabric Lakehouse called Landing_Dev. Build reads that binding from workspace configuration, while load, test and health read it from the Catalogue, so the same commands run against either environment.

2. Build

Build compares the repository with the current Fabric estate and applies the structural changes. It creates and maintains:

  • Schemas and folders
  • Delta tables in a Lakehouse
  • Tables and views in a Warehouse
  • Shortcuts between items
  • The runnable load code for each object, as a Python module or a T-SQL procedure
  • The metadata registration that makes all of it known

Build changes structure without loading data, so schema and object changes deploy independently from data movement.

Structure and data have separate lifecycles, so Weaver deploys them separately. You can install the shape of an entire platform into a fresh workspace without loading anything, or change a column type and rebuild without moving a row.

Builds are incremental, and the comparison runs against real state rather than a cached model: the Catalogue over TDS, a Lakehouse's views over Spark SQL, a Lakehouse's objects from storage, and a Warehouse over TDS.

Certification is per object. A rebuild removes certification from the selected objects and their descendants, and each one is certified again once it has built successfully.

3. The Catalogue

The Catalogue is Weaver's record of the installed estate and its operational state. Load, test and health use it directly.

The repository, Fabric and the Catalogue serve different roles.

The repository

The intended estate, held as files in source control. It changes when you write code.

Fabric

The physical platform, holding the actual Delta files, Warehouse tables and shortcuts. It changes when a build or a load runs.

The Catalogue

Weaver's record of what is installed and how it is running. It changes whenever either of the other two does.

The Catalogue lives as ordinary tables in the _ schema of a Fabric Warehouse you name. That Warehouse can be dedicated to Weaver or one you already use for your own schemas, because Weaver owns the _ schema and nothing else in it.

What it holds

What is installed

  • Every installed object, its role and its type
  • What depends on what
  • Shortcuts between items
  • Which physical Fabric item each logical item is bound to
  • Descriptions, columns, keys and foreign keys

How it is running

  • How far each object has loaded, as a bookmark
  • The current load outcome for each object
  • The current validation outcome for each object
  • Row counts for every insert, update and delete a load made
  • An append-only history of what has happened

Current state and history behave differently. A current-state row describes an object's current physical incarnation, so dropping and rebuilding the object ends that row: the new table has loaded nothing yet. History is append-only and a rebuild leaves it in place.

Because the Catalogue is a Warehouse, reading it is a TDS query, so a Warehouse-only project never starts a Spark session.

4. Load

Load runs the data work from the installed graph rather than from the repository.

It reads the Catalogue, derives the dependency graph from the rows already recorded there and runs each loadable object in order. The Catalogue tells it:

  • Which objects are loadable, and which are views that materialise nothing
  • What depends on what, across Fabric items as well as inside them
  • How far each object has already processed
  • What happened to each one last time

Naming an item loads everything it owns in dependency order, and naming none loads every installed item. Items are a hard boundary, so a dependency never pulls in an item you did not name.

Incremental loading, row-level change handling, rejected rows and recovery after a failure are covered in the mechanics below.

5. Test

Validations are part of the installed estate rather than a separate layer beside it.

A Test or an Assumption is authored under the item it belongs to, discovered like any other object, compiled by a build and installed alongside the tables it reads. It joins the same dependency graph, and its result is recorded in the Catalogue rather than only printed.

Weaver keeps two kinds distinct.

Test

A Test compares an expected relation with an actual one and passes when the symmetric difference is empty, reporting both missing and unexpected rows.

Assumption

An Assumption identifies rows that violate a condition the pipeline relies on, so it passes when the result is empty. It has no second side to correlate, so it declares no primary key.

Both compile to independently runnable primitives, so a T-SQL validation becomes a stored procedure that can be executed without Weaver.

Neither materialises a data object. A Test carries an ordinary Schema.Object identity so it can be named and recorded, but it is held apart from the documents an item materialises, so it never becomes table or view DDL. Weaver identifies artefacts by their declared role, which is why weaver load does not run validations.

6. Health

Health reports the current state of the estate rather than the outcome of a single command.

It reads the Catalogue and interprets state across the whole installed estate, which lets it flag an object that loaded successfully but is now stale because a source loaded again afterwards. Answering that needs the installed dependency graph, not just the last run's result.

Health reports:

  • Objects whose last load failed or was blocked upstream
  • Objects behind their sources, where an ancestor has loaded more recently
  • Objects with no settled load recent enough to count as current
  • Validations that are currently failing
  • Certified objects that are not physically there

By default anything without a settled load in the last 24 hours counts as stale, and --as-of moves that threshold.

The mechanics underneath

How Weaver handles dependency discovery, shortcuts, incremental state and failure.

Dependency discovery

Python dependencies

Weaver discovers Python dependencies from imports and symbol references.

Lakehouse/Landing/Tables/Sales__Customer.py
# The dependency is this line. Nothing else declares it.
from Files.Sales__Customers import Sales__Customers

from weaver import Table


class Sales__Customer(Table):
    def read(self):
        exported = Sales__Customers(self).spark_path()
        return self.spark.read.option("header", True).csv(exported)

T-SQL dependencies

Weaver discovers T-SQL dependencies from the relations referenced in the query, so there is no Jinja, no macros and no ref().

Warehouse/Curated/Sales.CustomerByRegion.sql
select c.[Customer id]
     , c.[Customer name]
     , r.[Region name]
  from [Sales].[Customer] c
  join [Sales].[Region] r on r.[Region code] = c.[Region code];

Discovery is static, so Weaver never imports your object modules to find out what they depend on. Building the graph runs none of your code and needs no Fabric session.

Shortcuts

A Warehouse cannot read Delta files, so it reads a Lakehouse through its SQL endpoint. In Weaver that shortcut is declared in the repository and becomes a node in the dependency graph.

Warehouse/Curated/shortcuts.yml
logical:
  Warehouse/Curated/Sales.Customer: Lakehouse/Landing/Tables/Sales.Customer

The Warehouse object then selects from [Sales].[Customer] as though it were local. Both sides are logical names that the Catalogue resolves, so neither item needs to know where the other is physically built. Build creates the shortcut, and load runs the Warehouse object after the Lakehouse table it reads.

Incremental load and bookmarks

Weaver records how far each object has processed as a bookmark: one row per loadable table or folder, holding the UTC instant immediately before its most recent clean load began.

A bookmark advances only after a clean load. A run that rejects rows leaves the bookmark unchanged, as does a run that fails, and an object that is dropped and rebuilt loses its bookmark entirely so the next load reads everything.

If the bookmark is behind, data may be replayed. Advancing it too far risks skipping data, so Weaver only advances it after a clean load.

In a Lakehouse, Python reads the bookmark directly and uses it to select what to process.

an incremental folder read
def read(self):
    # Files changed after the last clean load, and when.
    return Source__Export(self).files_since(self.bookmark())

There is a matching deleted_since(bookmark) for files that have been retired. An object with no bookmark row reads as an instant far in the past, so the first run is a full load without needing a special case.

Warehouse incremental behaviour is different. Weaver maintains the bookmark for every loadable Warehouse table and uses it to determine whether a Static table has already been loaded, but authored T-SQL does not read a bookmark window of its own. For a Warehouse table, incremental behaviour is about what a missing key means.

Incremental: true changes how absence is interpreted. A non-incremental keyed table treats the source as complete, so a key that is missing retires the target row. An incremental table treats the source as a window, so a key it does not carry says nothing about the target. Incremental requires a primary key, because there is otherwise nothing to reconcile against.

Change handling

When a keyed table loads, Weaver classifies every incoming row as an insert, update or delete before writing anything. The classification is itself a relation, so the load can evaluate the change before applying it.

Two kinds of problem are handled differently.

A bad incoming row

Recoverable. The row is refused with a reason and set aside, whether that is a blank primary key, a null in a column declared not null, a duplicate primary key or a duplicate unique key. --fault-tolerant controls whether the surviving rows load or the whole load stops.

A change that would leave the target invalid

Not recoverable. No single row is at fault, so the load stops before writing anything. Fault tolerance does not override this, because it governs incoming rows while this concerns the validity of the target itself.

A stability gate covers the case where nothing is individually wrong but the change is unexpectedly large. Each table declares how much change it treats as normal, and by default a load stops if it would delete more than 5% or update more than 20% of the target. The gate is not consulted below a million rows, so at the defaults a load has to remove more than 50,000 rows or change more than 200,000 before it applies.

Every gate runs before anything is written, so refusing a load means not starting it rather than unwinding it.

Failure and recovery

Partial failure is a normal operating condition in large pipelines, so what matters is the state of the estate afterwards.

  • Outcomes are recorded. The result of each object goes into the Catalogue, so the next command and the next person can both read it.
  • Dependent work is blocked. An object whose source did not load is recorded as blocked, which is a distinct outcome from having failed on its own account.
  • State advances only where processing completed cleanly. A bookmark moves after a clean load and nothing else, so a partial run cannot leave the next one believing a window was read.
  • Recovery continues from recorded state. The next run reads what the previous one left and picks up from there.

By default a load stops at the first failure. --fault-tolerant continues down branches that do not depend on the failure, which suits a scheduled run where most of the estate should still load.

weaver health then reads the recorded state and reports what is currently wrong, without reconstructing it from logs.
