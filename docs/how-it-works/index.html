One project. One set of operations.

Build the definitions, Load the data, Test the result and inspect Health. Repeat the same loop as the project grows.

1. Keep the definitions in a project

Write Python and SQL beneath their Lakehouse or Warehouse. Keep native model and Report definitions under PowerBI. Workspace configuration maps those logical items to their physical destinations.

workspace-config.yml 
workspace: Analytics
catalogue: Warehouse/Catalogue
targets:
  Lakehouse/Landing: Landing_Dev
  Warehouse/Curated: Curated_Dev
  SemanticModel/Sales: Sales_Dev
  Report/Sales: Sales_Report_Dev

Change the configuration for production; keep the source files the same.

2. Build the definitions

Build creates or changes Tables, Views, Shortcuts, load code and validation definitions. It also deploys native semantic models and linked Reports.

Build the source-data items first, then the models and Reports. Structural deployment and data loading are separate, so you can review a definition change before moving data.

3. Load and refresh in dependency order

Load runs installed Table and Folder work, then refreshes selected semantic models after their managed sources. Dependencies put the work in order across the estate.

Each data consumer keeps its own processing progress. The catalogue records outcomes, changed rows and the work left after a failure. Reports use the refreshed model’s data.

4. Test the results

Tests compare expected and actual rows; Assumptions return rows that violate a condition. Use SQL, Python or DAX for the item you are checking.

A model’s DAX result can be compared with SQL calculated independently from its Lakehouse or Warehouse source. Validation belongs with the definitions it checks.

5. Inspect the estate with Health

One Health report brings Build, Load and Test state together for the managed estate. It includes Lakehouse and Warehouse work, model refreshes and their validations.

An upstream change can make downstream data or a previously passing Test stale. Health shows that relationship, rather than treating yesterday’s successful run as today’s answer.

Weaver reads dependencies from the code

Python imports and supported T-SQL references supply dependencies. Spark SQL Tables and Views require explicit declarations.

Python

Sales__Customer.py 
from Files.Sales__Customers import Sales__Customers
from weaver import Table

class Sales__Customer(Table):
    def read(self):
        exported = Sales__Customers(self).spark_path()
        return (
            self.spark.read.option("header", True)
            .csv(exported)
            .selectExpr("`Customer id`", "`Customer name`", "`Region code`")
            .dropDuplicates(["Customer id"])
        )

The import tells Weaver to load the customer files before the Delta table.

T-SQL

Sales.CustomerByRegion.sql 
select c.[Customer id]
     , c.[Customer name]
     , r.[Region name]
  from [Sales].[Customer] c
  join [Sales].[Region] r
    on r.[Region code] = c.[Region code];

The query tells Weaver to load both Warehouse relations before the join. If one comes from a Lakehouse shortcut, Weaver still puts the work in the right order.
