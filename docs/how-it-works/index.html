From project to an operable Fabric estate

A Weaver project describes the estate you want. Build installs it and records what exists. Load, test and health then work from that installed state.

One lifecycle, with the stages kept distinct

projectthe estate in source
→
buildinstall its structure
→
Cataloguerecord installed state
→
load · test · healthoperate what is installed

Separate stages let you deploy a schema change without loading data, run data work without parsing a changing source tree, and ask what is current after the command that created it has finished.

1. The project names the estate logically

Each object lives under the Lakehouse or Warehouse that owns it. A separate workspace configuration maps those logical items to physical Fabric targets.

workspace-config.yml
workspace: Analytics
catalogue: Warehouse/Catalogue

targets:
  Lakehouse/Landing: Landing_Dev
  Warehouse/Curated: Curated_Dev

The project continues to refer to Lakehouse/Landing and Warehouse/Curated. Change the configuration to point at production; do not rewrite the objects or their references.

2. Build installs structure, not data

weaver build compares the project with Fabric and applies the structural difference.

It creates and maintains schemas, folders, Delta tables, Warehouse tables and views, shortcuts, validations and the code each load will run. It also records the installed objects and their dependencies in the Catalogue.

A fresh workspace can receive the whole platform shape before a row moves. A later column or shortcut change can deploy without turning into an accidental reload.

Build limits its work to the selected change and affected downstream objects. It leaves unrelated parts of the estate untouched.

3. The Catalogue makes the installed estate durable

The Catalogue is a Fabric Warehouse containing Weaver's view of what is installed and how it is running.

Installed state

Objects, physical bindings, dependencies, shortcuts, columns and keys. Load and test operate on this installed model rather than whatever happens to be in a developer's checkout.

Operational state

Bookmarks, load and validation outcomes, row-change counts and history. A failed run leaves enough state to distinguish what succeeded, failed and was blocked.

Because the Catalogue persists, later runs know what they are acting on and where the previous clean load stopped.

4. Load, test and health use the same estate

Load

Runs installed objects in dependency order across Fabric items. Bookmarks keep each object's position, and independent branches can continue when fault-tolerant loading is appropriate.

Test

Runs the Tests and Assumptions installed beside the objects they validate, then records their current outcomes in the Catalogue.

Health

Reports current estate state: failed or blocked loads, stale objects, failing validations and installed objects missing from Fabric.

A table can load successfully and become stale when an upstream object loads again. Health can see that because it reads outcomes and dependencies together.

The code supplies the graph

Weaver reads Python imports, SQL references and shortcut declarations. It does not ask you to repeat those dependencies in a separate orchestration file.

Python

Sales__Customer.py
from Files.Sales__Customers import Sales__Customers
from weaver import Table

class Sales__Customer(Table):
    def read(self):
        exported = Sales__Customers(self).spark_path()
        return (
            self.spark.read.option("header", True)
            .csv(exported)
            .selectExpr("`Customer id`", "`Customer name`", "`Region code`")
            .dropDuplicates(["Customer id"])
        )

The import places the table after the file acquisition.

T-SQL

Sales.CustomerByRegion.sql
select c.[Customer id]
     , c.[Customer name]
     , r.[Region name]
  from [Sales].[Customer] c
  join [Sales].[Region] r
    on r.[Region code] = c.[Region code];

The query places the Warehouse table after both relations it reads.

When one relation is a shortcut to another Fabric item, the same graph crosses that boundary. Load order, affected-change selection and staleness all use it.
