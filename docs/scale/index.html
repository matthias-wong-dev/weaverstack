Built for scale

Weaver uses one dependency and operational model across the estate, whether a project contains a small number of objects or many Fabric items and dependency layers. Incremental builds limit structural changes to the affected objects, while bookmarks and persistent operational state allow data processing to continue from previous runs.

How the model scales

One dependency graph

Every object sits in a single graph spanning Lakehouses, Warehouses, Python, Spark SQL and T-SQL. Ordering, layering and impact analysis all read from it, so adding items does not add coordination work.

Incremental builds

A build compares the repository against the installed estate and applies only the difference. Changing one object removes certification from its descendants, and the rest of the estate is left alone.

Loads sized by the change

A keyed load classifies inserts, updates and deletes before writing, and bookmarks let an incremental object read only the window since its last clean load. Load cost follows the size of the change rather than the size of the table.

Persistent operational state

The Catalogue records how far each object loaded, what failed and what is behind its sources. As an estate grows, that state is what makes targeted recovery possible instead of a full rerun.

Performance testing

Large-estate performance and incremental-build benchmarks are in preparation and will be published here.
