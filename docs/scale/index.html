Built for scale

Weaver uses the same model for a handful of objects or many Fabric items and dependency layers. It builds only what changed and records each object's load position, so a large estate does not require a large rebuild or a full reload.

How the model scales

One dependency graph

Weaver keeps every object in one graph, across Lakehouses, Warehouses, Python, Spark SQL and T-SQL. The same dependency and operating model extends across additional Fabric items.

Incremental builds

Build compares your repository against what is already installed and applies the difference. When you change one object, Weaver un-certifies it and everything downstream of it, and leaves the rest of the estate alone.

Loads sized by the change

Bookmarks and incremental loading can limit the source data processed on each run, while keyed loads classify the incoming change before writing.

Persistent operational state

Weaver records how far each object loaded, what failed and what is now behind its sources. On a large estate that is what lets you rerun the part that broke instead of the whole thing.

Performance testing

We are preparing large-estate performance and incremental-build benchmarks, and will publish them here.
