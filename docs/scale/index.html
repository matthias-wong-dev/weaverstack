For teams with 3 objects to those with 3,000.

A few files should not need a framework-building project. Thousands of objects should not need thousands of little frameworks.

More objects, the same way of working

These are illustrative milestones, not technical thresholds or required team sizes.

  1. 3

    Two spreadsheets and a table over them.

    Even a team of one benefits from repeatable definitions, version control and a place for checks. A little structure is enough. Source files can remain outside Weaver’s ownership.

  2. 30

    Organise before the tangle becomes another project.

    Dependencies and the effect of a change stop fitting comfortably in one person’s head. Keep them with the project rather than in a separate set of pipelines and conventions.

  3. 300

    The surrounding engineering starts interacting.

    Incremental loads, bookmarks, failures, endpoint synchronisation, metadata and logging are no longer separate little chores. The question becomes which framework to use, rather than whether to keep managing them all manually.

  4. 3,000

    Small repeated costs become large ones.

    A coherent framework, adopted or home-grown, is needed to operate the estate consistently. Each consumer needs its own processing progress; recovery needs to reach the right work. The developer should not have to maintain all that machinery.

Keep useful work moving

Run independent work together

Build actions and Load/Test work have resource limits and an optional total invocation cap. Ready work with the longest downstream chain starts first; this is not an optimal duration-aware scheduler.

Wait for the tables that are actually read

Supported SQL endpoint refresh and publication barriers follow the upstream objects their consumers need. Other ready Lakehouse work can continue beside them.

Stop an empty incremental window early

After staging is counted, an empty supported window can finish without the remaining change-application work, unless it claims a deletion.

Spend less time on repeated setup

Batched operations, cached metadata, asynchronous execution and fair Spark pools reduce repeated overhead. Notebook and local entry points use the same supported operation semantics.

What a measured 3,000-object run did

Historical benchmark from PR #193, not a fresh result for this documentation release. A synthetic F64 estate used one Lakehouse and two Warehouses: 2,144 tables, 816 views and 40 folders, with 30 business columns.

All seven measured operations
Operation Time Work
Build from empty 13m 48s 5,372 actions
First Load 61m 20s 2,185 nodes; approximately 4.05B rows inserted across the estate
Unchanged Build 1m 17s No actions
Unchanged Load 7m 57s 2,185 nodes; no changed rows
Day 1 Load 19m 25s Approximately 5.75M inserted, 2.03M updated, 40,910 deleted
Day 2 Load 13m 05s Approximately 5.70M inserted, 1.98M updated, 44,563 deleted
Day 3 Load 12m 56s Approximately 5.66M inserted, 1.86M updated, 33,105 deleted

The run used 24 Spark lanes and 12 lanes per Warehouse. Those were benchmark settings, not defaults or supported maxima. Nine convergence Tests passed after the first Load and each changed day.

Rows inserted across several layers are not distinct source records. Declared objects, scheduled Load nodes and physical Build actions count different things. The dependency fan-in includes declared waits without the corresponding join workload; an arbitrary warehouse with the same row count may behave very differently. This does not measure 3,000 semantic models or Report rendering.

Where the overhead went

Targeted endpoint refresh reduced that component of the initial Build from 9m 41s to 1m 49s, and of the unchanged Load from 6m 41s to 19s. Syncing only the tables needed through the endpoint avoided asking Fabric to refresh every table.

In the same 60-node Spark probe, 4 lanes took 208s; 8 took 140s; 16 took 85s; and 24 took 60s, within one Spark application on F64. More ready work could run together. These are observations from the investigation, not universal tuning recommendations.

Earlier whole-run totals also changed workload width and incremental design, so they are not a controlled speedup comparison. Simulated scheduler times are not in the measured-results table. Later PR #218 exercised 3,000 objects at --scale 0.01; those results do not inherit this run’s volume or timings.
