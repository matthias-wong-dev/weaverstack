More objects should not mean more coordination models

As a Fabric estate grows, Weaver keeps dependencies, physical bindings and operational state in the same model. The graph gets larger; the number of orchestration systems you maintain does not.

Growth follows the dependency graph

Adding another Lakehouse, Warehouse or branch of work adds nodes and edges to the estate Weaver already understands.

One graph across items

Python, Spark SQL and T-SQL objects remain in one graph even when they occupy different Fabric items. A new item does not require a parallel schedule to connect it to the old ones.

Work follows the affected subgraph

A build applies the selected structural change and follows its downstream impact. A load runs objects in dependency order. Neither operation pulls in unrelated branches.

The operating model does not become more complicated in proportion to the number of Fabric items.

State narrows recovery

Running everything again is an expensive recovery policy for a large estate. Weaver records enough state to identify the work that remains.

Bookmarks

Each loadable object keeps its position after a clean run. Incremental work can resume from that point rather than reading the whole source again.

Independent branches

A failed object blocks its descendants. Other branches can continue when you choose fault-tolerant loading, without pretending the failed branch succeeded.

Estate health

Current outcomes and dependencies reveal what failed, what was blocked and what has fallen behind a source that loaded later.

Development can branch without cloning the data

Mirror forks the installed Catalogue, then lets a development workspace borrow source data for the items it does not need to rebuild.

Keep unchanged data in place

Warehouse relations appear through views and Lakehouse relations through OneLake shortcuts. A development estate can be complete without making a second physical copy of every table and folder.

Materialise only where work diverges

Build a selected item into its own development target. The rest of the estate remains mirrored, with logical dependencies and load state still visible to Weaver.

terminal
weaver mirror --no-item --yes
weaver build --item Warehouse/Model=Warehouse/Model_Dev

The development workspace configuration names the source catalogue as mirror: and the fork as catalogue:.

Scale here means coordination

This is a claim about engineering work, not Fabric capacity or runtime performance. Increasing object and item counts need not produce the same increase in hand-maintained orchestration, environment bindings and recovery bookkeeping.
